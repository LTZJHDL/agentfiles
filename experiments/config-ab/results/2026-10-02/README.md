# 首轮配置实验结果：2026-10-02

新配置在这两项任务中产生了更多实际分工，交付质量与旧配置相当。效率结果不一致：功能任务按统一费率折算的成本下降，缺陷任务上升；两项任务各自的完成时间都更长。因此，本轮支持“精简引导仍能完成任务，较便宜的 worker 可以承担工作”，尚不支持“整套新配置普遍更快、更省”。

这里比较 10 月 1 日旧配置 A 的 run-01、run-02，以及 10 月 2 日新配置 B 的 run-03、run-04。统计只包含最初的开发轮次及其全部子 agent，排除之后的“提交改动”轮次和本次评估。每项任务每组仅运行一次。

## 交付结果

四个工作副本的起始内容均与冻结版本一致，同任务的 A/B 起始 Git tree 完全相同。四次实际 prompt 与原 prompt 去除空白差异后相同；日志中实际加载的 AGENTS.md 分别匹配 A/B 快照。四个主 agent 均为 `gpt-6-astra xhigh`。

| 任务 | 旧配置 A | 新配置 B | 成果判断 |
| --- | --- | --- | --- |
| 导入预览 | run-01：外部验收 9/9，项目测试 26/26 | run-03：外部验收 9/9，项目测试 23/23 | 相当 |
| 统计缺陷 | run-02：外部验收 8/8，项目测试 19/19 | run-04：外部验收 8/8，项目测试 17/17 | 相当 |

代码比较由一个未获知配置对应关系的独立 agent 先行评审，主 agent 再核对关键实现与文档；这不是人工盲评。两份功能实现几乎同构：解析后生成共享导入计划，预览只读当前记录，正式导入一次事务写入全部变更。两份缺陷修复也一致：复用列表的当前记录查询，再过滤、汇总，删除原有错误查询。未发现任务范围内的实质缺陷。

测试数量不同不代表可靠性等级不同。run-01 额外检查规范化、Unicode 身份及数据库元数据；run-03 用 SQLite authorizer 检查没有写入动作，并覆盖损坏数据库。run-02 的过滤组合更广；run-04 将回归测试放进独立文件，并明确覆盖日期倒退仍取最新修订。它们都覆盖了本任务的关键风险。

文字也各有取舍。run-01 的 README 有具体预览输出、计数含义及“行数不等于最终记录数”的解释；run-03 提供可直接复制的 PowerShell 命令。最终回复均准确交代完成情况和限制。旧配置的缺陷回复还直接解释了为什么两种错误抵消条数差异，却产生合计 22；新配置在过程更新中给出了同样解释。没有充分依据判定新配置的表达明显更好。

## 实际协作

| Run | 实际子 agent | 主 agent 保留的工作 |
| --- | --- | --- |
| 01，A 功能 | 1 个 worker，实际 Astra medium，编写预览测试 | 核心实现、文档、集成验证 |
| 02，A 缺陷 | 1 个 explorer，5.6 Luna medium，核对数据及契约 | 复现、诊断、回归测试、修复与验证 |
| 03，B 功能 | 2 个 worker，6.1 Sol high，分别编写测试和文档；1 个 explorer，6 Luna medium，复核实现 | 核心实现、额外边界检查、集成与最终解释 |
| 04，B 缺陷 | 1 个 explorer，6 Luna medium，核对契约、数据和方案；1 个 worker，6.1 Sol high，编写回归测试 | 复现、诊断、影响检查、核心修复与集成验证 |

所有委派均显式使用 `fork_turns="none"`，没有更深的子 agent。新配置的 worker 确实完成了可以落地的测试和文档，说明较便宜的角色承担了实际交付；旧配置也已经会主动委派，并不是没有协作。

新配置同时增加了协调工作。功能任务主 agent 的模型请求从 15 次增至 22 次；缺陷任务从 14 次增至 27 次。run-04 在 10:52:27 启动测试 worker，等待其在旧实现上确认失败，worker 于 10:56:46 完成；主 agent 期间发了 3 次面向该 worker 的消息、调用 4 次等待，随后才应用修复。这个顺序有验证价值，也把测试产出放在了修复的关键路径上。不能将等待全部算作浪费，但它没有体现出理想的并行加速。

run-03 的额外代码复核没有发现任务范围内的实质缺陷；提出的 `revisions` view 情况位于工具约定的数据库结构之外。独立复核可以提高信心，这次却没有证据表明它提升了最终成果质量。两个 B run 中，explorer 还承担了部分判断性复核，说明实际选角没有严格沿着“检索”与“判断”的边界划分；这值得观察，不宜据此增加硬性禁令。

operator、professor、kami 在这四次开发中均未被调用。由此无法评价 operator 与 worker 的选择边界，也不能判断 professor 是否被描述得过于昂贵。两道题要求具体、项目较小，对品味、问题定义和开放式表达的区分能力有限；kami 未被使用也不构成失败。所有派发都指定了角色，默认子 agent 配置的变化也未得到直接检验。

## 时间与消耗

| 指标 | A 功能 | B 功能 | A 缺陷 | B 缺陷 |
| --- | ---: | ---: | ---: | ---: |
| 开发轮次耗时 | 8 分 55 秒 | 9 分 34 秒 | 7 分 56 秒 | 10 分 34 秒 |
| 模型请求，含全部子 agent | 20 | 43 | 16 | 41 |
| 输入 tokens，含缓存 | 870,095 | 1,897,344 | 737,893 | 1,808,723 |
| 其中缓存输入 tokens | 766,336 | 1,803,648 | 652,416 | 1,691,264 |
| 输出 tokens，含推理 | 14,201 | 20,085 | 10,853 | 12,547 |
| 统一 Standard 费率折算 credits | 62.85 | 52.72 | 43.43 | 56.72 |

用量来自 11 个会话日志的逐请求 `token_usage_record.usage`。按初始 `root_turn_id` 选择范围，以 `response_id` 去重，并逐线程核对各轮累计用量。父日志的记录属于父线程，子线程另行计入；没有把多次累计 token 统计相加，推理 token 也没有在输出之外重复计费。

最后一行是比较代理指标，不是实际扣费。按 2026-10-02 查阅的 [OpenAI Standard credits 费率](https://learn.chatgpt.com/docs/pricing)，对每个线程计算：`((输入 − 缓存输入) × 输入费率 + 缓存输入 × 缓存费率 + 输出 × 输出费率) / 1,000,000`，再相加。历史速度档位未核实，因此统一假设 Standard。官方也明确区分 credits 价格与订阅内含额度消耗；不能用这个值推断套餐百分比。

在这个口径下，B 功能比 A 低 **16.1%**，B 缺陷比 A 高 **30.6%**。两项合计 A 为 106.28、B 为 109.44，约高 **3.0%**，没有显示总体节省。耗时分别增加 **7.2%** 和 **33.1%**。这些是本次样本的描述，不是稳定优势或劣势的估计。

成本结构比总额更有启发：功能任务的子 agent 折算成本从 19.02 降至 5.67，主 agent 却从 43.83 升至 47.05；缺陷任务的主 agent 从 43.26 升至 54.03，额外子 agent 成本仅约 2.69。B 两项任务的主 agent 分别占折算总成本的 **89%**、**95%**。这意味着降低子 agent 单价确实可能有效，但更关键的是委派是否减少了昂贵主线程的实际工作，而不是单纯多调用几个便宜角色。

## 比较条件的实际变化

- **运行时版本变化。** 日志记录 A 的 Codex CLI 为 `0.155.0-alpha.16`，B 为 `0.159.2`。应用升级、运行时行为和时段差异都可能影响结果，不能把变化全归因于 AGENTS.md 或角色文字。
- **B 的两次任务并行。** 按北京时间，run-03 为 10 月 2 日 10:46:36–10:56:10，run-04 为 10:48:04–10:58:39，重叠约 8 分 6 秒；A 两次没有重叠。逐线程 token 仍可分别归属，耗时却可能受共享资源影响。B 批次更早一起完成也不能算作 subagent 配置带来的加速。
- **worker 后端与冻结快照不同。** B 快照记录 `gpt-6-sol high`，实际三个 worker 均为 `gpt-6.1-sol high`。本报告按实际模型计算，保留原快照，避免事后改变实验定义。
- **额度数据不足。** 准备记录中的用量、速度和配置核对字段没有补填。日志只能补回部分事实：任务内主线程周额度观测依次为 4%→5%、5%→5%、6%→6%、6%→6%，且首个观测发生在任务开始之后。这是全账户、整数精度的观测，B 又存在重叠，不能视为四次任务的精确额度消耗。缓存命中也明显不同，已按日志分别计入折算。

这些限制不抹去“成果合格、调用了什么角色”等直接观察，却限制了因果和实际成本结论。

## 对配置的判断

可以继续使用这套更清晰、精简的角色配置。本轮没有观察到放松详细规则后，质量、主线程对关键源码的理解或最终集成失守；worker 后端替换后也交付了可用成果。但“更积极委派”已经出现，“总任务更省”仍是待验证假设。

暂不根据这四次结果继续增补 AGENTS.md 规则，也不急着调整 professor 描述。现有引导已经要求考虑协调与返工成本，当前样本更需要检验这种判断是否在适当规模的任务中发挥作用。

**后续观察备忘（2026-10-02，待验证）：** 委派是否减少了主线程负担，或带来了值得额外成本的质量收益？本轮发现了一次值得关注的等待依赖，尚未证明配置文字存在缺陷。

在实际工作中遇到有代表性的案例时，简要记录任务规模、委派内容，以及它如何影响主线程的工作、等待和最终成果。既保留协调或返工过多的案例，也保留节省工作、发现关键问题或改善判断的案例；不必为每个任务增加记录负担。若同类问题在不同任务中反复出现，再检查是否与配置引导有关，并据此决定是否调整；后续证据也可能让这条疑点消退。

下一轮应固定同一运行时版本、实际 worker 后端和速度，依次运行各任务，在新的干净副本中交换 A/B 顺序并保留所有结果。先复跑这两题以观察方向是否重复，再增加一项有多个可独立交付部分的任务，以及一项需要设计或表达判断的开放任务。让 agent 自行选角，重点看委派是否替代了主线程工作、是否形成等待依赖，以及整体质量与成本；不设角色调用配额。

# 共享表达规范对复杂回复的影响

本文保留第二轮试测的结果与阶段判断。2026-09-26 归档时决定暂不采用 split 版本，完整依据见[归档决定与两轮比较](../comparison.md)。

这轮试测发现了局部、轻微的可读性收益，但没有发现所有复杂回复都受益。Open SWE 流程题的两次独立生成，两位匿名评审均偏好规范组；跨项目比较题有一些相同方向的支持；DeerFlow 的信息与状态题则一次偏好默认组、一次持平。两组都能支持预设理解问题，事实核验也未发现相对于所给材料的实质错误。

因此，Human-Facing Expression 有作为复杂解释辅助材料的价值；目前证据仍不足以支持“撰写任何面向用户的内容前都必须读取”。有帮助的地方是把分支条件、依赖与比较关系安排得更便于理解。效果取决于具体安排，长度本身不能说明是否需要规范。本轮没有修改 AGENTS.md、SKILL.md 或共享规范。

## 怎样比较

使用本地 deepagents、open-swe 和 deer-flow 的文件，为三道真实解释任务冻结材料。现有材料已经覆盖流程、项目比较、信息与状态三类组织问题，本轮没有再扩展到其他候选仓库。

| 任务 | 读者需要弄清的关系 |
| --- | --- |
| T1：Open SWE 从 Slack 请求到 PR | 消息、thread、run、沙箱和 agent 如何连接；运行中与完成后的补充有何不同；AGENTS.md 与测试要求怎样起作用 |
| T2：deepagents、Open SWE、DeerFlow 比较 | 各项目的层次、现成能力与待补集成；实现内部代码助手时怎样选择与组合 |
| T3：DeerFlow 的资料、子代理与记忆 | 独立对话与共享文件怎样并存；压缩与长期记忆的区别；新对话能否继续使用旧资料；目录隔离与容器隔离的区别 |

每题生成两组、每组两个副本，共十二份答案、六对比较。每份答案使用独立的默认 worker 上下文，不继承主对话，不指定字数、章节或展示形式。默认组 C 遵循现有环境及基础表达要求；规范组 G 唯一增加的任务要求，是写回复前读取并遵循共享规范。两组使用相同题目和材料，不能自行搜索或调用其他写作技能。全部生成记录均符合各自的规范读取要求。

评价分为三个部分：三个事实评审各核查一题的四份匿名答案；两位可读性评审比较六对匿名答案，第二位交换 X/Y 并倒转顺序；四个独立读者代理从各自收到的答案中回答理解问题。每个读者只看到每题的一个版本，不能看材料或其他版本。主代理知道条件，负责证据复核与综合，自己的判断不称为盲评。

任务、生成与评价规则在生成前固定，见[方案](protocol.md)、[题目](cases.json)、[可读性判据](readability-rubric.md)和[理解问题](reader-questions.json)。

## 可读性结果

表中“略好”是对整篇答案的轻微偏好。没有一对被判为全篇有实质差距；其中 T1 第二次生成的条件关系维度，被第二位评审判为有实质改善。

| 任务与副本 | 第一位评审 | 第二位评审 | 主要观察 |
| --- | --- | --- | --- |
| T1，第 1 次，P01 | 规范组略好 | 规范组略好 | 并列展示队列补充、Slack 再次提及、完成后新 run，条件更容易比较 |
| T1，第 2 次，P05 | 规范组略好 | 规范组略好 | 流程图较早定位 AGENTS.md；补充消息的分支集中呈现 |
| T2，第 1 次，P02 | 规范组略好 | 持平 | 规范组较早解释框架层次；默认组将已有组合与待设计组合放得更集中 |
| T2，第 2 次，P06 | 规范组略好 | 规范组略好 | 借 Web 框架类比解释 harness，接着讨论依赖与组合，减少读者切换主题 |
| T3，第 1 次，P03 | 默认组略好 | 默认组略好 | 默认组先给机制与作用范围总表；规范组夹入身份和存储配置细节 |
| T3，第 2 次，P04 | 持平 | 持平 | 默认组总览便于比较；规范组更早解释 thread，并用具体文件读写说明共享 |

第一位评审偏好规范组 4 对、默认组 1 对、持平 1 对；第二位分别为 3、1、2 对。两位在五对的总体判断上一致，剩下一对是“规范组略好”与“持平”的差别。这是六对答案的两次评价，不能计成十二个独立生成样本。

### 收益具体发生在哪里

T1 两次生成都出现同一种区别。默认组先介绍队列机制，再分别解释 Slack 入口使用 interrupt 的实现边界与完成后的行为。必要信息都在，但比较几种情况时，读者需要把相邻段落中的条件重新组合。规范组直接把“队列已有消息”“Slack 再次提及”“完成后启动新 run”放在同一张情况表中，比较时少了一次重组。这支持的是条件关系更清楚，并非表格天然优于段落。完整对照见[匿名答案 P01、P05](blind-comparison.md)。

T2 第二次生成中，规范组先用读者熟悉的 Web 框架关系解释 harness，再在能力表后集中说明 Open SWE → deepagents → LangGraph，以及 DeerFlow 哪些层次重叠、组合还需什么工作。默认组也解释了这些关系，但中间展开了四步代码工作流。对这道选型题，两位评审都认为前一种顺序更便于回答核心疑问。对照见[匿名答案 P06](blind-comparison.md)。

T3 提供了相反的例子。默认组先用“保存或传递什么／作用范围”总表区分文件、子代理上下文、压缩和长期记忆。规范组第一份答案沿任务过程解释，也有清楚的例子，却在跨会话记忆部分加入无认证用户 ID 和绝对 storage_path 的配置细节，随后才回到记忆注入与旧文件访问。细节与项目有关，对当前理解任务帮助有限。两位评审都略偏好默认组，见[匿名答案 P03](blind-comparison.md)。

这些差别与规范鼓励的“建立总体理解、集中相关信息、按读者任务选择细节”相符，但本轮不能确认是哪一条要求产生了作用，也不能把所有生成差异都归因于规范。

## 事实、信息提取与篇幅

事实评审没有发现实质错误或影响理解的遗漏。T3 四份答案都省略了文件路径还包含 user_id 这一维度，被记录为部分覆盖，但评审认为不影响题目所问的线程与跨会话边界。这里测的是对提供材料的忠实程度；T2 的概述材料有实现覆盖限制，见后文。

理解问题共 48 项，每组 24 项。读者代理从两组答案中都能提取依据，没有出现“无法从答案确定”的项目。默认组被标为 23 项直接给出、1 项需要推断；规范组为 24 项直接给出。默认组有 18 项需连接不同段落，规范组有 15 项。所有引文都能逐字回查原答案。这些是模型提取与定位记录，分类仍带有判断成分，不能据此宣称人类理解率或阅读速度提高。

两组篇幅接近，变化因题目而异：

| 任务 | 默认组平均字符数 | 规范组平均字符数 | 规范组变化 |
| --- | ---: | ---: | ---: |
| T1 | 2,273 | 2,268 | -0.2% |
| T2 | 2,270 | 2,140.5 | -5.7% |
| T3 | 1,868.5 | 2,154 | +15.3% |
| 六份答案总计 | 12,823 | 13,125 | +2.4% |

统计不含空白字符，包含标识符、引用和 Markdown 标记；不是 token 数，也不作为质量评分。T1 篇幅几乎不变仍有组织收益；T3 增加篇幅没有带来总体优势。

## 对是否引入规范的判断

第一轮[基础行为试测](../behavior-pilot/report.md)没有发现明确对话优势；这轮在复杂回复中观察到了可重复的局部偏好。这使“规范可能帮助组织复杂关系”更有依据，但不能直接得出“长度越大越有效”：两轮题目和评审方法都有变化，本轮也没有让同一任务仅改变长短。

对当前设计，三个判断应分开：

- **共享文件的组织方式仍然合理。** 文档写作和对话可以复用原则，各自保留适用条件。上一轮两个文档任务未见实质退步；本轮没有重新检验文档技能，也未证明拆分在所有文档任务中无影响。
- **复杂回复有可观察的局部收益。** 需要解释多种分支、跨组件依赖或多项比较时，相关原则有价值。默认回复已经具备不少相同能力，收益体现为具体安排更好，幅度有限。
- **所有回复必读的要求仍缺少依据。** 简短回复没有显示明确收益，复杂回复也并非一致受益；实际加载成本与条件触发效果尚未测量。若按需引用，判断依据应是读者需要理解哪些关系，而不宜只设长度或章节数门槛。这是依据试测提出的设计判断，尚不是经过验证的触发规则。

目前保留拆分试验即可，不据此将草稿中的全局必读要求部署到正式 AGENTS.md。模型默认表达能力变化后，这些边际收益也需要重新判断；本轮没有比较不同模型版本。

## 结果的适用范围

两组都继承当前环境已有的表达指令，因此测的是额外读取规范的边际作用。只用了三类技术解释、每组两个副本，不能据此作显著性、严格等效或普遍有效的结论。两位模型评审及读者代理也不能替代真实用户阅读；交换展示位置能减少位置偏差，但不能消除共同的模型偏好。

各生成使用相同默认 worker 配置，没有主动指定不同模型或思考强度，也没有控制采样 seed；记录未锁定底层模型构建版本及全部推理参数。本轮未测试真实 AGENTS 自动加载、长会话中的持续遵循、首次进度回复、读取延迟或 token 成本。

材料按本地文件冻结，并记录版本、全文哈希和原文摘录，没有运行项目。T2 的概述材料未包含 T1 中区分 Slack interrupt 与消息队列的完整代码；部分答案复述了 README 的工作中消息注入概括。因此，该题的事实通过不能当作对当前 Slack 实现的完整核验，更不能作为某一组更准确的证据。详见[材料核对说明](source-audit.md)。

## 记录与复核

原始材料见 [T1](materials/T1.md)、[T2](materials/T2.md)、[T3](materials/T3.md)；各自的 sources.json 保存来源、范围、哈希和原文。仓库版本见 [source-revisions.json](source-revisions.json)，规范内容与哈希见 [guide-snapshot.json](guide-snapshot.json)。

十二份回复可在[匿名对照](blind-comparison.md)中连续阅读；条件对应见 [pair-map.json](pair-map.json)，精确生成提示见 [generation-manifest.json](generation-manifest.json)。评价原文见[评审一](readability-review-1.json)、[评审二](readability-review-2.json)；事实审查与独立读者记录保留在同目录。归一化结果见 [summary.json](summary.json)。

`freeze_materials.py` 负责冻结证据，已有答案后禁止重跑以免改变实验输入。`assemble.py` 生成匿名评审包，`summarize.py` 汇总结果，`validate.py` 检查 JSON、分组、答案哈希、材料摘录、48 项理解问题的引文及报告链接。验证结果见 [validation.json](validation.json)。冻结材料保留源码行末空白，不按报告正文的空白检查修改。复核检查不代替事实判断或可读性评价。

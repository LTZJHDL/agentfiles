````text
636: ### Sub-Agents
637: 
638: Complex tasks rarely fit in a single pass. DeerFlow decomposes them.
639: 
640: The lead agent can spawn sub-agents on the fly — each with its own scoped context, tools, and termination conditions. Sub-agents run in parallel when possible, report back structured results, and the lead agent synthesizes everything into a coherent output. When token usage tracking is enabled, completed sub-agent usage is attributed back to the dispatching step.
641: 
642: This is how DeerFlow handles tasks that take minutes to hours: a research task might fan out into a dozen sub-agents, each exploring a different angle, then converge into a single report — or a website — or a slide deck with generated visuals. One harness, many hands.
643: 
644: ### Sandbox & File System
645: 
646: DeerFlow doesn't just *talk* about doing things. It has its own computer.
647: 
648: Each task gets its own execution environment with a full filesystem view — skills, workspace, uploads, outputs. The agent reads, writes, and edits files. It can view images and, when configured safely, execute shell commands.
649: 
650: With `AioSandboxProvider`, shell execution runs inside isolated containers. With `LocalSandboxProvider`, file tools still map to per-thread directories on the host, but host `bash` is disabled by default because it is not a secure isolation boundary. Re-enable host bash only for fully trusted local workflows.
651: 
652: This is the difference between a chatbot with tool access and an agent with an actual execution environment.
653: 
654: ```
655: # Paths inside the sandbox container
656: /mnt/user-data/
657: ├── uploads/          ← your files
658: ├── workspace/        ← agents' working directory
659: └── outputs/          ← final deliverables
660: ```
661: 
662: ### Context Engineering
663: 
664: **Isolated Sub-Agent Context**: Each sub-agent runs in its own isolated context. This means that the sub-agent will not be able to see the context of the main agent or other sub-agents. This is important to ensure that the sub-agent is able to focus on the task at hand and not be distracted by the context of the main agent or other sub-agents.
665: 
666: **Summarization**: Within a session, DeerFlow manages context aggressively — summarizing completed sub-tasks, offloading intermediate results to the filesystem, compressing what's no longer immediately relevant. This lets it stay sharp across long, multi-step tasks without blowing the context window.
667: 
668: **Strict Tool-Call Recovery**: When a provider or middleware interrupts a tool-call loop, DeerFlow now strips provider-level raw tool-call metadata on forced-stop assistant messages and injects placeholder tool results for dangling calls before the next model invocation. This keeps OpenAI-compatible reasoning models that strictly validate `tool_call_id` sequences from failing with malformed history errors.
669: 
670: ### Long-Term Memory
671: 
672: Most agents forget everything the moment a conversation ends. DeerFlow remembers.
673: 
674: Across sessions, DeerFlow builds a persistent memory of your profile, preferences, and accumulated knowledge. The more you use it, the better it knows you — your writing style, your technical stack, your recurring workflows. Memory is stored locally and stays under your control.
675: 
676: Memory updates now skip duplicate fact entries at apply time, so repeated preferences and context do not accumulate endlessly across sessions.
````

````text
405: 
406: **Components**:

414: - Per-agent per-user memory at `{base_dir}/users/{user_id}/agents/{agent_name}/memory.json`
415: - Custom agent definitions (`SOUL.md` + `config.yaml`) are also per-user at `{base_dir}/users/{user_id}/agents/{agent_name}/`. The legacy shared layout `{base_dir}/agents/{agent_name}/` remains read-only fallback for unmigrated installations
416: - `user_id` is resolved via `get_effective_user_id()` from `deerflow.runtime.user_context`

418: - Absolute `storage_path` in config opts out of per-user isolation

420: 
421: **Data Structure** (stored in `{base_dir}/users/{user_id}/memory.json`):
422: - **User Context**: `workContext`, `personalContext`, `topOfMind` (1-3 sentence summaries)
423: - **History**: `recentMonths`, `earlierContext`, `longTermBackground`
424: - **Facts**: Discrete facts with `id`, `content`, `category` (preference/knowledge/context/behavior/goal), `confidence` (0-1), `createdAt`, `source`
425: 
426: **Workflow**:
427: 1. `MemoryMiddleware` filters messages (user inputs + final AI responses), captures `user_id` via `get_effective_user_id()`, and queues conversation with the captured `user_id`
````

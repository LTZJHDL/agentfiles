````text
35: 
36: Open SWE makes the same core architectural decisions as the best internal coding agents. Here's how it maps to the patterns described in [this overview](https://x.com/kishan_dahya/status/2028971339974099317) of Stripe's Minions, Ramp's Inspect, and Coinbase's Cloudbot:
37: 
38: ### 1. Agent Harness — Composed on Deep Agents
39: 
40: Rather than forking an existing agent or building from scratch, Open SWE **composes** on the [Deep Agents](https://github.com/langchain-ai/deepagents) framework — similar to how Ramp built on top of OpenCode. This gives you an upgrade path (pull in upstream improvements) while letting you customize the orchestration, tools, and middleware for your org.
41: 
42: ```python
43: create_deep_agent(
44:     model="anthropic:claude-opus-4-6",
45:     system_prompt=construct_system_prompt(repo_dir, ...),
46:     tools=[http_request, fetch_url, commit_and_open_pr, linear_comment, slack_thread_reply],
47:     backend=sandbox_backend,
48:     middleware=[ToolErrorMiddleware(), check_message_queue_before_model, ...],
49: )
50: ```
51: 
52: ### 2. Sandbox — Isolated Cloud Environments
53: 
54: Every task runs in its own **isolated cloud sandbox** — a remote Linux environment with full shell access. The repo is cloned in, the agent gets full permissions, and the blast radius of any mistake is fully contained. No production access, no confirmation prompts.
55: 
56: Open SWE supports multiple sandbox providers out of the box — [Modal](https://modal.com/), [Daytona](https://www.daytona.io/), [Runloop](https://www.runloop.ai/), and [LangSmith](https://smith.langchain.com/) — and you can plug in your own. See the [Customization Guide](CUSTOMIZATION.md#1-sandbox) for details.
57: 
58: This follows the principle all three companies converge on: **isolate first, then give full permissions inside the boundary.**
59: 
60: - Each thread gets a persistent sandbox (reused across follow-up messages)
61: - Sandboxes auto-recreate if they become unreachable
62: - Multiple tasks run in parallel — each in its own sandbox, no queuing
63: 
64: ### 3. Tools — Curated, Not Accumulated
65: 
66: Stripe's key insight: *tool curation matters more than tool quantity.* Open SWE follows this principle with a small, focused toolset:
67: 
68: | Tool | Purpose |
69: |---|---|
70: | `execute` | Shell commands in the sandbox |
71: | `fetch_url` | Fetch web pages as markdown |
72: | `http_request` | API calls (GET, POST, etc.) |
73: | `commit_and_open_pr` | Git commit + open a GitHub draft PR |
74: | `linear_comment` | Post updates to Linear tickets |
75: | `slack_thread_reply` | Reply in Slack threads |
76: 
77: Plus the built-in Deep Agents tools: `read_file`, `write_file`, `edit_file`, `ls`, `glob`, `grep`, `write_todos`, and `task` (subagent spawning).
78: 
79: ### 4. Context Engineering — AGENTS.md + Source Context
80: 
81: Open SWE gathers context from two sources:
82: 
83: - **`AGENTS.md`** — If the repo contains an `AGENTS.md` file at the root, it's read from the sandbox and injected into the system prompt. This is your repo-level equivalent of Stripe's rule files: encoding conventions, testing requirements, and architectural decisions that every agent run should follow.
84: - **Source context** — The full Linear issue (title, description, comments) or Slack thread history is assembled and passed to the agent, so it starts with rich context rather than discovering everything through tool calls.
85: 
86: ### 5. Orchestration — Subagents + Middleware
87: 
88: Open SWE's orchestration has two layers:
89: 
90: **Subagents:** The Deep Agents framework natively supports spawning child agents via the `task` tool. The main agent can fan out independent subtasks to isolated subagents — each with its own middleware stack, todo list, and file operations. This is similar to Ramp's child sessions for parallel work.
91: 
92: **Middleware:** Deterministic middleware hooks run around the agent loop:
93: 
94: - **`check_message_queue_before_model`** — Injects follow-up messages (Linear comments or Slack messages that arrive mid-run) before the next model call. You can message the agent while it's working and it'll pick up your input at its next step.
95: - **`open_pr_if_needed`** — After-agent safety net that commits and opens a PR if the agent didn't do it itself. This is a lightweight version of Stripe's deterministic nodes — ensuring critical steps happen regardless of LLM behavior.
96: - **`ToolErrorMiddleware`** — Catches and handles tool errors gracefully.
97: 
98: ### 6. Invocation — Slack, Linear, and GitHub
99: 
100: All three companies in the article converge on **Slack as the primary invocation surface**. Open SWE does the same:
101: 
102: - **Slack** — Mention the bot in any thread. Supports `repo:owner/name` syntax to specify which repo to work on. The agent replies in-thread with status updates and PR links.
103: - **Linear** — Comment `@openswe` on any issue. The agent reads the full issue context, reacts with 👀 to acknowledge, and posts results back as comments.
104: - **GitHub** — Tag `@openswe` in PR comments on agent-created PRs to have it address review feedback and push fixes to the same branch.
105: 
106: Each invocation creates a deterministic thread ID, so follow-up messages on the same issue or thread route to the same running agent.
107: 
108: ### 7. Validation — Prompt-Driven + Safety Nets
109: 
110: The agent is instructed to run linters, formatters, and tests before committing. The `open_pr_if_needed` middleware acts as a backstop — if the agent finishes without opening a PR, the middleware handles it automatically.
111: 
112: This is an area where you can extend Open SWE for your org: add deterministic CI checks, visual verification, or review gates as additional middleware. See the [Customization Guide](CUSTOMIZATION.md#6-middleware) for how.
113:
````

````text
636: ### Sub-Agents
637: 
638: Complex tasks rarely fit in a single pass. DeerFlow decomposes them.
639: 
640: The lead agent can spawn sub-agents on the fly — each with its own scoped context, tools, and termination conditions. Sub-agents run in parallel when possible, report back structured results, and the lead agent synthesizes everything into a coherent output. When token usage tracking is enabled, completed sub-agent usage is attributed back to the dispatching step.
641: 
642: This is how DeerFlow handles tasks that take minutes to hours: a research task might fan out into a dozen sub-agents, each exploring a different angle, then converge into a single report — or a website — or a slide deck with generated visuals. One harness, many hands.
643: 
644: ### Sandbox & File System
645: 
646: DeerFlow doesn't just *talk* about doing things. It has its own computer.
647: 
648: Each task gets its own execution environment with a full filesystem view — skills, workspace, uploads, outputs. The agent reads, writes, and edits files. It can view images and, when configured safely, execute shell commands.
649: 
650: With `AioSandboxProvider`, shell execution runs inside isolated containers. With `LocalSandboxProvider`, file tools still map to per-thread directories on the host, but host `bash` is disabled by default because it is not a secure isolation boundary. Re-enable host bash only for fully trusted local workflows.
651: 
652: This is the difference between a chatbot with tool access and an agent with an actual execution environment.
653: 
654: ```
655: # Paths inside the sandbox container
656: /mnt/user-data/
657: ├── uploads/          ← your files
658: ├── workspace/        ← agents' working directory
659: └── outputs/          ← final deliverables
660: ```
661: 
662: ### Context Engineering
663: 
664: **Isolated Sub-Agent Context**: Each sub-agent runs in its own isolated context. This means that the sub-agent will not be able to see the context of the main agent or other sub-agents. This is important to ensure that the sub-agent is able to focus on the task at hand and not be distracted by the context of the main agent or other sub-agents.
665: 
666: **Summarization**: Within a session, DeerFlow manages context aggressively — summarizing completed sub-tasks, offloading intermediate results to the filesystem, compressing what's no longer immediately relevant. This lets it stay sharp across long, multi-step tasks without blowing the context window.
667: 
668: **Strict Tool-Call Recovery**: When a provider or middleware interrupts a tool-call loop, DeerFlow now strips provider-level raw tool-call metadata on forced-stop assistant messages and injects placeholder tool results for dangling calls before the next model invocation. This keeps OpenAI-compatible reasoning models that strictly validate `tool_call_id` sequences from failing with malformed history errors.
669: 
670: ### Long-Term Memory
671: 
672: Most agents forget everything the moment a conversation ends. DeerFlow remembers.
673: 
674: Across sessions, DeerFlow builds a persistent memory of your profile, preferences, and accumulated knowledge. The more you use it, the better it knows you — your writing style, your technical stack, your recurring workflows. Memory is stored locally and stays under your control.
675: 
676: Memory updates now skip duplicate fact entries at apply time, so repeated preferences and context do not accumulate endlessly across sessions.
````

````text
371: ### IM Channels System (`app/channels/`)
372: 
373: Bridges external messaging platforms (Feishu, Slack, Telegram, DingTalk) to the DeerFlow agent via the LangGraph Server.
374: 
375: 
376: **Architecture**: Channels communicate with Gateway through the `langgraph-sdk` HTTP client (same as the frontend), ensuring threads are created and managed server-side. The internal SDK client injects process-local internal auth plus a matching CSRF cookie/header pair so Gateway accepts state-changing thread/run requests from channel workers without relying on browser session cookies.
377: 
378: **Components**:
379: - `message_bus.py` - Async pub/sub hub (`InboundMessage` → queue → dispatcher; `OutboundMessage` → callbacks → channels)
380: - `store.py` - JSON-file persistence mapping `channel_name:chat_id[:topic_id]` → `thread_id` (keys are `channel:chat` for root conversations and `channel:chat:topic` for threaded conversations)
381: - `manager.py` - Core dispatcher: creates threads via `client.threads.create()`, routes commands, keeps Slack/Telegram on `client.runs.wait()`, and uses `client.runs.stream(["messages-tuple", "values"])` for Feishu incremental outbound updates
382: - `base.py` - Abstract `Channel` base class (start/stop/send lifecycle)
383: - `service.py` - Manages lifecycle of all configured channels from `config.yaml`
384: - `slack.py` / `feishu.py` / `telegram.py` / `dingtalk.py` - Platform-specific implementations (`feishu.py` tracks the running card `message_id` in memory and patches the same card in place; `dingtalk.py` optionally uses AI Card streaming for in-place updates when `card_template_id` is configured)
385: 
386: **Message Flow**:
387: 1. External platform -> Channel impl -> `MessageBus.publish_inbound()`
388: 2. `ChannelManager._dispatch_loop()` consumes from queue
389: 3. For chat: look up/create thread through Gateway's LangGraph-compatible API
390: 4. Feishu chat: `runs.stream()` → accumulate AI text → publish multiple outbound updates (`is_final=False`) → publish final outbound (`is_final=True`)
391: 5. Slack/Telegram chat: `runs.wait()` → extract final response → publish outbound
392: 6. Feishu channel sends one running reply card up front, then patches the same card for each outbound update (card JSON sets `config.update_multi=true` for Feishu's patch API requirement)
393: 7. DingTalk AI Card mode (when `card_template_id` configured): `runs.stream()` → create card with initial text → stream updates via `PUT /v1.0/card/streaming` → finalize on `is_final=True`. Falls back to `sampleMarkdown` if card creation or streaming fails
394: 8. For commands (`/new`, `/status`, `/models`, `/memory`, `/help`): handle locally or query Gateway API
395: 9. Outbound → channel callbacks → platform reply
396: 
397: **Configuration** (`config.yaml` -> `channels`):
398: - `langgraph_url` - LangGraph-compatible Gateway API base URL (default: `http://localhost:8001/api`)
399: - `gateway_url` - Gateway API URL for auxiliary commands (default: `http://localhost:8001`)
400: - In Docker Compose, IM channels run inside the `gateway` container, so `localhost` points back to that container. Use `http://gateway:8001/api` for `langgraph_url` and `http://gateway:8001` for `gateway_url`, or set `DEER_FLOW_CHANNELS_LANGGRAPH_URL` / `DEER_FLOW_CHANNELS_GATEWAY_URL`.
````

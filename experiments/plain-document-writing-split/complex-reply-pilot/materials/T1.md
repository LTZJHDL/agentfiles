````text
36: Open SWE makes the same core architectural decisions as the best internal coding agents. Here's how it maps to the patterns described in [this overview](https://x.com/kishan_dahya/status/2028971339974099317) of Stripe's Minions, Ramp's Inspect, and Coinbase's Cloudbot:
37: 
38: ### 1. Agent Harness — Composed on Deep Agents
39: 
40: Rather than forking an existing agent or building from scratch, Open SWE **composes** on the [Deep Agents](https://github.com/langchain-ai/deepagents) framework — similar to how Ramp built on top of OpenCode. This gives you an upgrade path (pull in upstream improvements) while letting you customize the orchestration, tools, and middleware for your org.
41: 
42: ```python
43: create_deep_agent(
44:     model="anthropic:claude-opus-4-6",
45:     system_prompt=construct_system_prompt(repo_dir, ...),
46:     tools=[http_request, fetch_url, commit_and_open_pr, linear_comment, slack_thread_reply],
47:     backend=sandbox_backend,
48:     middleware=[ToolErrorMiddleware(), check_message_queue_before_model, ...],
49: )
50: ```
51: 
52: ### 2. Sandbox — Isolated Cloud Environments
53: 
54: Every task runs in its own **isolated cloud sandbox** — a remote Linux environment with full shell access. The repo is cloned in, the agent gets full permissions, and the blast radius of any mistake is fully contained. No production access, no confirmation prompts.
55: 
56: Open SWE supports multiple sandbox providers out of the box — [Modal](https://modal.com/), [Daytona](https://www.daytona.io/), [Runloop](https://www.runloop.ai/), and [LangSmith](https://smith.langchain.com/) — and you can plug in your own. See the [Customization Guide](CUSTOMIZATION.md#1-sandbox) for details.
57: 
58: This follows the principle all three companies converge on: **isolate first, then give full permissions inside the boundary.**
59: 
60: - Each thread gets a persistent sandbox (reused across follow-up messages)
61: - Sandboxes auto-recreate if they become unreachable
62: - Multiple tasks run in parallel — each in its own sandbox, no queuing
63: 
64: ### 3. Tools — Curated, Not Accumulated
65: 
66: Stripe's key insight: *tool curation matters more than tool quantity.* Open SWE follows this principle with a small, focused toolset:
67: 
68: | Tool | Purpose |
69: |---|---|
70: | `execute` | Shell commands in the sandbox |
71: | `fetch_url` | Fetch web pages as markdown |
72: | `http_request` | API calls (GET, POST, etc.) |
73: | `commit_and_open_pr` | Git commit + open a GitHub draft PR |
74: | `linear_comment` | Post updates to Linear tickets |
75: | `slack_thread_reply` | Reply in Slack threads |
76: 
77: Plus the built-in Deep Agents tools: `read_file`, `write_file`, `edit_file`, `ls`, `glob`, `grep`, `write_todos`, and `task` (subagent spawning).
78: 
79: ### 4. Context Engineering — AGENTS.md + Source Context
80: 
81: Open SWE gathers context from two sources:
82: 
83: - **`AGENTS.md`** — If the repo contains an `AGENTS.md` file at the root, it's read from the sandbox and injected into the system prompt. This is your repo-level equivalent of Stripe's rule files: encoding conventions, testing requirements, and architectural decisions that every agent run should follow.
84: - **Source context** — The full Linear issue (title, description, comments) or Slack thread history is assembled and passed to the agent, so it starts with rich context rather than discovering everything through tool calls.
85: 
86: ### 5. Orchestration — Subagents + Middleware
87: 
88: Open SWE's orchestration has two layers:
89: 
90: **Subagents:** The Deep Agents framework natively supports spawning child agents via the `task` tool. The main agent can fan out independent subtasks to isolated subagents — each with its own middleware stack, todo list, and file operations. This is similar to Ramp's child sessions for parallel work.
91: 
92: **Middleware:** Deterministic middleware hooks run around the agent loop:
93: 
94: - **`check_message_queue_before_model`** — Injects follow-up messages (Linear comments or Slack messages that arrive mid-run) before the next model call. You can message the agent while it's working and it'll pick up your input at its next step.
95: - **`open_pr_if_needed`** — After-agent safety net that commits and opens a PR if the agent didn't do it itself. This is a lightweight version of Stripe's deterministic nodes — ensuring critical steps happen regardless of LLM behavior.
96: - **`ToolErrorMiddleware`** — Catches and handles tool errors gracefully.
97: 
98: ### 6. Invocation — Slack, Linear, and GitHub
99: 
100: All three companies in the article converge on **Slack as the primary invocation surface**. Open SWE does the same:
101: 
102: - **Slack** — Mention the bot in any thread. Supports `repo:owner/name` syntax to specify which repo to work on. The agent replies in-thread with status updates and PR links.
103: - **Linear** — Comment `@openswe` on any issue. The agent reads the full issue context, reacts with 👀 to acknowledge, and posts results back as comments.
104: - **GitHub** — Tag `@openswe` in PR comments on agent-created PRs to have it address review feedback and push fixes to the same branch.
105: 
106: Each invocation creates a deterministic thread ID, so follow-up messages on the same issue or thread route to the same running agent.
107: 
108: ### 7. Validation — Prompt-Driven + Safety Nets
109: 
110: The agent is instructed to run linters, formatters, and tests before committing. The `open_pr_if_needed` middleware acts as a backstop — if the agent finishes without opening a PR, the middleware handles it automatically.
111: 
112: This is an area where you can extend Open SWE for your org: add deterministic CI checks, visual verification, or review gates as additional middleware. See the [Customization Guide](CUSTOMIZATION.md#6-middleware) for how.
````

````text
77:             return None
````

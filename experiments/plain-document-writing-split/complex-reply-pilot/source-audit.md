# 材料核对说明

本轮只读取本地项目文件，未启动项目、联网获取最新版本或执行其中的命令。材料保留源码原文和行号；三个仓库的 HEAD 见 source-revisions.json，所选文件的全文 SHA256 及摘录见 materials/*.sources.json。HEAD 不能代表未提交内容，摘录和哈希才是本轮实际输入的记录。

T1 的 Open SWE 文档概述与代码存在两处重要区别：Slack 所示入口调用带 interrupt 策略的 runs.create；消息队列中间件存在，但不能把这个 Slack 入口统一解释为排队。PR 兜底会先检查工具返回载荷，没有载荷或载荷包含 success 键会跳过，且没有测试结果门槛。主代理直接核对了相应函数，并同时提供给两组。

T3 的 DeerFlow 需要区分子代理独立消息列表与继承的 sandbox/thread_data/thread_id。上下文压缩前也有记忆入队钩子；动态记忆注入代码在首次会话提醒时引入记忆，同日后续轮次不刷新，跨日只更新日期。主代理直接核对了这些边界。源资料中的概述有时更宽泛，评分按包内具体代码优先。

T2 为定位比较使用了概述性材料，没有包含 T1 的全部实现。它的 Open SWE README 把工作中的追加消息概括为下一次模型调用前注入。部分答案按该材料复述了这一点。这不应被用作已经核实的当前 Slack 行为，也不应成为某一条件“更事实准确”的证据；该题事实审查测的是对所给材料的忠实程度，未覆盖全项目实现一致性。T1 才提供了区分路径的代码。报告会保留这一材料限制。

只读检索代理提供了位置线索；主代理发现部分行号已不适合实际文件、以及“每轮记忆注入”的概括过宽，重新读取后修正。冻结脚本检查了每个范围确实存在，不直接把检索摘要当作权威内容。

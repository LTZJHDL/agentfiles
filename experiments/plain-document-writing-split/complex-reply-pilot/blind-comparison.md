# 复杂回复匿名对照

X/Y 按题交换；这里不显示哪份答案使用了规范。

## P01 · Open SWE 请求到 PR

我会写 Python，但没有用过 LangGraph。我想理解 Open SWE：在 Slack 里让它修一个仓库的 bug 之后，消息、agent、线程和沙箱之间到底怎样配合，最后又怎么得到 PR？如果我在它工作时补充一句要求，和它完成后再回复一句，有什么区别？仓库里的 AGENTS.md 在哪里起作用？它说有自动开 PR 的兜底，这是否也意味着测试一定通过？

### X

Open SWE 把 Slack 对话、模型的执行状态和实际改代码的环境连在一起。理解它时，先区分这几个概念：

| 概念 | 在这里负责什么 |
|---|---|
| Slack 线程 | 你提需求、补充要求、接收结果的对话串 |
| LangGraph thread | 保存 agent 对话状态的标识；同一 Slack 对话串映射到同一个 ID |
| run | 在这个 thread 上发起的一次执行；同一个 thread 可以承接后续执行 |
| agent | 调用模型，并根据模型选择使用读写文件、执行命令、开 PR 等工具 |
| 沙箱 | 实际存放仓库、修改文件、运行命令的远程 Linux 环境 |

这里的 thread 不必理解成 Python 的操作系统线程。它主要用于把对话状态、消息队列和沙箱关联到同一个任务。

从 Slack 请求到 PR，大致经过以下过程：

1. **接收请求并确定对话。** 你在 Slack 中 @机器人，可以用 `repo:owner/name` 指定仓库。入口排除机器人消息，并取频道 ID 和 Slack 根消息时间戳，生成确定性的 LangGraph thread ID。因此，同一 Slack 对话串里的后续请求能找到相同的任务标识。（T1-S01、S02、S04）
2. **组装模型要读的上下文。** 服务获取 Slack 消息，把仓库、触发者、对话内容和最新要求整理成用户消息，再为名为 `agent` 的图创建一次 run。仓库和 Slack 回复位置等信息同时放进运行配置。README 概括为“完整线程历史”，但具体代码会选择上下文，起点可能是线程开头，也可能是上一次 @机器人的消息，不能理解为每次都重发所有历史。（T1-S03）
3. **准备沙箱和 agent。** 服务按 thread 查找沙箱：没有就创建并克隆仓库；已有则复用缓存或重新连接，并尝试拉取仓库。沙箱不可达时可以重建。因此，沙箱通常跨后续消息保留，但不等于其中未保存的内容永不丢失。随后服务用 `create_deep_agent(...)` 组装模型、工具、沙箱后端和中间件。（T1-S06、S07）
4. **循环处理代码工作。** 你可以把 agent 看成一个“模型判断下一步 → 调工具 → 读取结果 → 再判断”的循环。文件和命令操作通过沙箱后端落到仓库里；中间件则是在这个循环的固定位置执行的 Python 逻辑，例如模型调用前读取补充消息，agent 结束后检查 PR 提交路径。它也支持用 `task` 工具拆出子任务，但并非每次修 bug 都必须这样做。（T1-S01、S05、S07）
5. **提交并回到 Slack。** 正常路径是 agent 完成修改和检查后调用 `commit_and_open_pr`，提交、推送并创建草稿 PR；成功后用 `slack_thread_reply` 发摘要和 PR 链接。提示词明确要求：只有工具返回成功及 PR 链接，才能声称 PR 已创建或更新。（T1-S01、S10、S11）

**工作中补充要求，与完成后再回复，差别在于是否还有正在运行的模型循环可以接收消息。**

工作中，项目提供了消息队列机制：进入该 thread 队列的补充内容，会在下一次模型调用前按先后顺序合并成新的用户消息，加入对话状态。它不是立即打断正在执行的 shell 命令，也不能撤销已经做完的操作。（T1-S05）

完成后，原来的循环已经结束，需要在同一个 thread 上发起新的 run 才能继续；已有沙箱通常会复用。使用同一 Slack 对话串并再次 @机器人，是这份材料明确展示的触发方式。普通回复是否都会被接收，材料不足以确认。（T1-S03、S04、S06）

这里还有一个实现上的边界：材料展示了“消费队列”的中间件，却没有展示 Slack 消息何时入队的完整分流代码；展示出的创建 run 路径还设置了 `multitask_strategy="interrupt"`。所以可以确认系统具备运行中接收队列消息的能力，但不能仅凭这些片段断言“工作中的每一条 Slack 补充都只会排队，绝不会中断当前 run”。

**`AGENTS.md` 在创建 agent、构造系统提示词时起作用。** 服务从沙箱中读取仓库根目录的 `AGENTS.md`，把内容放进系统提示词的 `<agents_md>` 段，作为仓库约定、检查要求和架构指导。文件不存在或为空就不注入。这段实现只自动读取根目录文件，没有展示对子目录同名文件的递归加载。它给模型提供指令，本身不是自动执行测试或拦截提交的程序。（T1-S07、S08、S12）

**自动开 PR 的兜底不意味着测试一定通过，甚至也不是无条件保证有 PR。** README 的说法比代码宽：实际 `open_pr_if_needed` 会先查找 `commit_and_open_pr` 的工具结果。找不到就直接跳过；结果里只要存在 `success` 字段，也会跳过，并不检查该字段是否为真。只有取得不含该字段的参数结果后，才继续检查未提交或未推送的修改，尝试提交到 `open-swe/{thread_id}` 分支，并在有 GitHub token 时推送、创建 PR；没有改动会跳过，异常会被记录。（T1-S09）

这个兜底里没有运行测试、读取测试结果或要求 CI 通过的判断。README 说 agent 被要求执行测试；给出的具体提示词片段明确要求格式化、lint、检查 diff，并在检查通过后提交。这些都是给模型的行为要求，不是这里展示出的强制测试关卡。因此，PR 链接只能说明提交产物已生成，测试是否通过仍要看实际执行结果和 CI 状态。（T1-S01、S09–S11）

### Y

Open SWE 把 Slack 请求接到一个能读代码、改文件和运行命令的 agent 上，再把结果提交到 GitHub。理解这条链路，先区分两个概念：**thread 是持续保存任务上下文的会话；run 是在这个会话上启动的一次执行。** 同一个 thread 可以先后有多次 run，沙箱则是与 thread 关联的代码工作环境。

从你在 Slack 里发出请求开始，流程是这样的：

1. **接收请求并找到会话。** 你提及机器人，可以用 `repo:owner/name` 指定仓库。入口用 Slack 的频道 ID 和线程时间戳生成固定的 LangGraph thread ID，所以在同一条 Slack 讨论里再次触发，会回到同一个任务会话。这里的 thread 不是 Python 的操作系统线程。（T1-S01、S02、S04）
2. **把聊天整理成模型输入。** 服务取出 Slack 讨论，组织仓库、发起人、对话上下文和最新请求，并带上回复 Slack 所需的信息。README 说会提供完整历史，但代码实际先选择上下文，起点可能是讨论开头，也可能是上一次提及机器人处，不能理解为每次都把全部历史重新发送。随后它在指定 thread 上创建一个 `agent` run；thread 不存在时会创建。（T1-S03）
3. **准备沙箱和仓库。** 服务优先复用该 thread 的沙箱连接，或通过记录的沙箱 ID 重连；没有沙箱时新建，并在里面克隆仓库。复用时会调用克隆或拉取仓库的逻辑。沙箱不可达时可以重建，因此“持久复用”不等于沙箱里的所有未提交文件永远不会丢失。（T1-S06）
4. **组装并运行 agent。** Open SWE 用 `create_deep_agent` 组合模型、系统指令、工具、沙箱 backend 和中间件。模型根据消息决定下一步，工具负责实际读写文件、执行 shell 命令、调用 GitHub 或回复 Slack；工具结果再供模型继续判断。Deep Agents 还提供 `task` 工具，允许主 agent 分派子任务，但不是每次修 bug 都必须使用子代理。（T1-S01、S07）
5. **提交结果并回报。** 正常路径要求 agent 完成检查、审阅 diff，再调用 `commit_and_open_pr` 提交和推送改动、创建 GitHub draft PR。成功后通过 `slack_thread_reply` 把摘要和 PR 链接发回原讨论。项目指令还明确要求：只有工具返回成功和 PR 链接，才能声称 PR 已创建或更新；无改动或报错时应如实报告。（T1-S01、S10、S11）

可以把 LangGraph 在这里理解成管理会话状态和执行过程的那一层：Slack 提供输入，agent 决定并调用工具，沙箱承载仓库和命令执行，GitHub 承载提交与 PR。消息上下文与沙箱文件是两类状态，通过同一个 thread 关联起来。

**工作中补充要求，与完成后再次触发，区别在于是否还有一次正在进行的 run。** 不过，这份代码里有两条机制，不能混为一谈：

| 情况 | 材料能够确认的行为 |
| --- | --- |
| 补充消息已经进入当前 thread 的队列 | `check_message_queue_before_model` 在下一次模型调用前读取队列，按顺序把内容合成一条新的用户消息加入会话，并清空队列。它不是在 shell 命令执行到一半时立即改写命令。 |
| Slack 中再次提及机器人，走所展示的入口 | 入口创建新的 run，并设置 `multitask_strategy="interrupt"`。若已有 run 在执行，采用中断策略，不能一概描述为“只入队，原 run 继续”。 |
| 上一轮已经完成，再在同一 Slack 讨论中提及机器人 | 在相同 thread 上启动新 run，并尝试复用关联沙箱，接着处理新要求；不是恢复一个始终在后台运行的模型调用。 |

队列代码证明了“已入队消息如何被消费”，但给出的片段没有展示 Slack 消息入队的完整路径。因此无法断言你工作中发出的每一句普通回复都会进入队列。所展示的 Slack 入口要求提及机器人，并忽略机器人消息；完成后只回复一句却不提及机器人，也不能据此保证会启动下一轮。（T1-S03—S05）

**`AGENTS.md` 在创建 agent、构造系统指令时起作用。** 仓库准备好后，服务读取沙箱中仓库根目录的 `AGENTS.md`，把非空内容放进系统指令的 `<agents_md>` 区块。编码约定、测试要求、架构约束因此会成为模型工作的依据。这里展示的是根目录文件读取，没有展示对子目录 `AGENTS.md` 的递归查找；这些文字也不会自动变成强制执行的测试程序。（T1-S07、S08、S12）

**自动开 PR 的兜底不代表测试一定通过，而且这份代码中的兜底范围比 README 的说法窄。** README 声称 agent 没开 PR 时会自动补上；实际 `open_pr_if_needed` 会先从会话中寻找 `commit_and_open_pr` 的工具结果：

- 没有可用结果，就直接跳过。因此 agent 完全没调用这个工具时，不能指望该中间件无条件补开 PR。
- 结果中只要存在 `success` 这个键，就跳过；代码没有检查它的值是否为 `true`，所以这也不是通用的失败重试机制。
- 只有得到不含该键的参数载荷，并且沙箱、仓库等条件满足、确有未提交改动或未推送提交时，才继续提交。有 GitHub token 才推送并创建 PR，目标分支为 `open-swe/{thread_id}`；异常会被记录。（T1-S09）

这段兜底代码没有运行测试，也没有检查测试结果。README 描述的验证主要依赖对 agent 的指令；所给具体指令明确要求格式化、lint 和检查 diff，但这些要求本身不构成“测试失败就禁止开 PR”的程序门槛。**拿到 PR 链接只说明产生了供审查的交付物；是否跑过测试、哪些测试通过，要看实际执行结果和 CI，不能从自动开 PR 推断。**（T1-S01、S09—S11）

## P02 · 三个项目的定位与选择

我看了 deepagents、Open SWE 和 DeerFlow，感觉它们都支持工具、子代理和沙箱，分不清到底是什么关系。我会 Python，也懂普通 Web 应用，但不熟悉 agent 框架。现在要做一个团队内部代码助手：同事从工作沟通工具发任务，它在隔离环境里改代码，产出供人审查的 PR。这三个项目分别能给我什么，需要自己补什么？它们是互相替代的选择，还是可以叠在一起？请结合这个目标给出判断，材料无法确定的地方也说明。

### X

就你要做的“同事从沟通工具发任务 → 隔离环境改代码 → 生成供人审查的 PR”，Open SWE 是最贴近目标的起点。deepagents 是它已经采用的底层组件；DeerFlow 则提供另一套通用 agent 框架和完整应用，适合同时需要研究、报告等多类任务的团队，但材料没有证明它已具备同样完整的代码到 PR 流程。

它们看起来都有工具、子代理和沙箱，是因为这些都是长任务所需的基础能力；真正影响选型的是，谁替你把消息入口、任务状态、执行环境和提交结果连成了流程。

| 项目 | 已经给你的东西 | 为你的目标仍需补齐或配置的部分 |
|---|---|---|
| deepagents | Python agent 运行骨架：任务规划、文件操作、子代理、上下文压缩，以及可配置的工具、模型和执行后端 | 沟通工具接入、消息与任务的对应关系、仓库准备、沙箱生命周期、Git/PR 操作、结果回传和团队权限规则 |
| Open SWE | 基于 deepagents 的代码助手：Slack/Linear 发起任务、线程复用沙箱、仓库上下文、运行中接收补充要求、提交并开 GitHub 草稿 PR、处理 PR 评论中的反馈 | 部署与凭据配置、仓库和沙箱提供商接入、团队权限与质量门槛；若入口不是现有支持的平台，还需接入适配 |
| DeerFlow | 通用 agent 框架加 Web 应用、Gateway API，以及飞书、Slack、Telegram、钉钉渠道；还提供技能、记忆、子代理和可配置执行环境 | 面向代码助手的仓库/分支管理、提交与 PR 流程、评审反馈回流和确定性质量检查；这些在给定材料中没有得到确认 |

这里“运行骨架”可以理解为：你给它模型、工具和任务，它负责组织模型调用、工具执行和多步工作的推进。deepagents 的 `create_deep_agent()` 返回一个编译好的 LangGraph 图；对你而言，可以先把它当作可调用的 Python agent 对象，再逐步使用 LangGraph 的流式输出、状态保存和检查点能力。它不是现成的团队代码助手。另外，材料里的远程沙箱、人工审批等部分功能介绍属于 Deep Agents CLI，不能据此认为只调用一次 SDK 构造函数就有了整套服务。（T2-S01–S03）

Open SWE 已把这套骨架接进了代码工作流。它调用 `create_deep_agent()`，传入沙箱后端、仓库相关系统说明、PR 和消息工具，以及运行前后的处理钩子。沟通工具里的同一线程或 issue 会对应稳定的任务线程；沙箱按线程复用，工作中发来的补充消息会在下一次模型调用前注入。仓库根目录的 `AGENTS.md` 会从沙箱读取并加入系统提示，适合放代码约定、测试要求和架构说明。它的 PR 工具创建的是草稿 PR，与“产出后交给人审查”的目标相符。（T2-S04–S07）

不过，自动开 PR 的兜底不等于测试通过。材料说明测试、格式化和 lint 主要靠提示要求 agent 执行；结束后的钩子负责补做提交和开 PR，没有证据表明它是强制测试闸门。若团队要求检查通过后才能进入某个阶段，需要增加确定性检查、CI 或审查门槛。同样，README 对沙箱安全性的概括不能证明你部署后的凭据和网络权限设置安全，实际隔离范围仍取决于配置。（T2-S05）

DeerFlow 也不是只有一个聊天网页。它明确拆成可发布的 `deerflow-harness` 框架包和应用层：前者负责 agent、工具、沙箱、技能等，后者负责 FastAPI Gateway 和沟通渠道。渠道会保存外部会话与任务线程的映射，通过 Gateway 创建和运行任务，再把结果发回。因此，如果团队主要使用飞书或钉钉，它已有的入口会有吸引力；但“有入口、能执行命令”还不能证明已经完成了从仓库到 PR 的工程流程。（T2-S10–S12）

选 DeerFlow 时还要区分执行模式：`AioSandboxProvider` 在隔离容器里执行 shell；`LocalSandboxProvider` 只是把文件工具映射到宿主机上的线程目录，宿主机 bash 默认关闭，因为这不是安全隔离边界。子代理各有独立上下文，也不代表各有独立容器。不能仅凭“线程隔离”就认定满足你的隔离改代码要求。（T2-S09）

它们的组合关系可以分成两种：

- **已有明确组合：Open SWE → deepagents → LangGraph。** 选择 Open SWE 时已经在使用 deepagents，不需要再把两者当成独立产品拼接一次。
- **需要自行设计的组合：DeerFlow 与 Open SWE。** 两者都使用 LangGraph，但材料没有说明 DeerFlow 依赖 deepagents，也没有给出它与 Open SWE 的现成集成方式。可以考虑让 DeerFlow 承接通用任务，把代码任务交给独立的 Open SWE 服务；这是架构设想，需要自己处理任务标识、状态、权限和结果回传，不能视为开箱即用。

我的判断是：若核心需求就是代码任务到 GitHub PR，且 Slack/Linear 入口合适，从 Open SWE 定制最直接；若你要完全自定产品流程，愿意自己建设消息、沙箱和交付环节，再选 deepagents；若飞书/钉钉和通用办公任务同样重要，DeerFlow 值得考虑，但应把代码到 PR 的流程视为待确认、可能需要自行实现的部分。给定材料没有性能、成本、成功率或完整权限实现的证据，无法据此判断谁更可靠，也不能量化各自的改造工作量。

### Y

针对“同事从沟通工具发任务 → 在隔离环境里改代码 → 产出供人审查的 PR”，**Open SWE 是最贴近目标的起点**。deepagents 是它已经采用的底层组件；DeerFlow 则是另一套更通用的完整应用和 agent 运行框架。它们能力有重叠，但不处于同一层，也不是三个必须叠加的组件。

你可以把 agent 理解为“模型反复判断下一步，再调用工具”的程序。这里的 harness 就是围绕这个循环提供文件操作、任务拆分、上下文管理等能力的运行框架；LangGraph 则是这些项目使用的运行基础。对你这个 Web 应用目标，关键是有没有把消息入口、会话状态、执行环境和 GitHub 交付接成完整流程。

| 项目 | 已经提供什么 | 围绕你的目标还要补什么 |
| --- | --- | --- |
| **deepagents** | 可在 Python 中创建、调用的 agent；计划、文件工具、子代理、上下文压缩；返回可使用流式输出和状态保存等 LangGraph 能力的运行图。 | 沟通平台接入、消息与会话的对应关系、仓库准备、隔离执行环境配置、GitHub 提交与 PR 流程、团队权限和验收规则。材料没有展示 SDK 自带这条完整业务链路。 |

依据：T2-S01～S07、T2-S08～S12。deepagents 的 README 另列了 CLI 的远程沙箱、审批等功能，不能据此认定一次 `create_deep_agent()` 调用就自动具备所有 CLI 集成（T2-S02、S03）。

Open SWE 与你的目标如何对应，可以直接沿着任务走一遍：

1. 同事在 Slack 线程中提及机器人，并可用 `repo:owner/name` 指定仓库。系统把线程历史交给 agent，用确定的线程 ID 把后续消息关联到同一个任务。
2. 仓库被克隆进云沙箱，同一线程的后续消息复用沙箱。agent 在里面读写代码、执行命令；仓库根目录的 `AGENTS.md` 用来提供代码约定和测试要求。
3. agent 调用 `commit_and_open_pr` 提交修改、创建 GitHub 草稿 PR，再向沟通线程返回结果和链接。工作中到来的补充消息会在后续模型调用前注入；agent 创建的 PR 也支持通过评论触发修订。（T2-S05～S07）

这条链路已经覆盖你要做的大部分应用层工作，所以使用 Open SWE 时，**无需再单独搭一套 deepagents 服务**：它通过 Python 的 `create_deep_agent(...)` 组合底层能力，自己提供工具、沙箱后端和执行前后的处理逻辑。这是材料明确存在的叠加关系（T2-S04、S05）。

DeerFlow 值得考虑的条件是：你的团队主要使用飞书或钉钉，或者代码助手只是更大范围内部助手的一部分，还要做研究、报告、文件处理等任务。它已有这些沟通渠道和通用应用基础，能减少入口及交互层的工作；代价是代码交付流程需要更多确认和开发。它还把可发布的 `deerflow-harness` 与应用层分开，沟通渠道属于应用层，不能只引入框架包就假定渠道服务也已具备（T2-S08、S10～S12）。

有两个区别会直接影响选择：

- **有子代理不等于有独立容器。** 子代理的上下文隔离，是模型看到的信息各自独立；执行隔离则取决于沙箱配置。DeerFlow 的 `AioSandboxProvider` 在隔离容器中执行命令，`LocalSandboxProvider` 只是把文件工具映射到宿主机的各线程目录，宿主机 bash 默认禁用，目录划分不是安全隔离边界。你的需求应采用真正隔离的执行环境（T2-S09）。
- **自动产出 PR 不等于质量检查通过。** Open SWE 要求 agent 运行格式化、lint 和测试，也有 agent 结束后补开 PR 的机制；但材料明确把确定执行的 CI 检查和审查关卡列为可扩展项。团队需要把“测试通过才能合并”等要求落实为实际检查，不能只依赖 agent 遵循文字规则（T2-S05、S07）。

因此，我会优先以 **Open SWE 作为内部代码助手的应用基础**；只有在需要自行掌控整套业务流程时，才直接从 deepagents 搭起；若多种沟通渠道和通用任务同样重要，则考虑以 DeerFlow 为基础补齐代码交付能力。

材料没有显示 DeerFlow 依赖 deepagents，也没有展示 DeerFlow 与 Open SWE 的现成连接方式。把两者接成“一个接消息、一个处理代码”可以作为定制架构设想，但线程关联、身份与权限传递、结果回流仍需自己设计。现有材料也不足以判断三者的代码修复成功率、运行成本、并发容量或团队权限是否满足你的实际部署要求。

## P03 · DeerFlow 长任务中的信息与状态

我会 Python，但第一次看 DeerFlow。假设我上传几份资料，让它并行研究、汇总出一份报告，过几天又新建对话继续讨论。我想弄清：子代理、workspace/uploads/outputs、上下文压缩和长期记忆分别保存或传递什么，它们之间怎么配合？子代理是否自动知道主代理之前的全部对话？新建对话后是否就能继续读取之前上传的资料？另外，本地模式里的线程隔离，是否等于每个子代理都在独立容器里？

### X

在你的场景里，DeerFlow 会把信息放在几个不同的地方：主代理负责分工和汇总，子代理各自处理任务；文件保存在当前对话所属的线程目录；上下文压缩帮助同一段长对话继续进行；长期记忆则把筛选后的信息带到后续对话。**子代理不会自动获得主代理的全部聊天记录，新对话也不会自动接上旧对话的上传目录。本地线程隔离更不等于每个子代理有一个容器。**

沿着“上传资料 → 并行研究 → 生成报告 → 几天后新建对话”来看，它们这样配合。

**上传后，资料先成为当前线程的文件。** 这里的线程就是用 `thread_id` 标识的一段对话。上传接口带有这个 ID，文件按线程保存，`UploadsMiddleware` 再把上传文件清单提供给代理；收到清单并不等于模型已经读过所有文件内容。（T3-S03、T3-S12）

代理看到的目录分工是：

| 目录 | 在这次研究中的用途 |
| --- | --- |
| `/mnt/user-data/uploads/` | 你上传的资料 |
| `/mnt/user-data/workspace/` | 研究笔记、提取结果等工作文件 |
| `/mnt/user-data/outputs/` | 最终报告等交付文件 |

这些目录保存的是文件。模型当下可见的对话消息、工具返回内容属于上下文，两者需要通过读写文件的工具衔接。把大段中间结果写入工作文件，可以减少对话里反复携带的内容；需要细节时再读取文件。（T3-S01）

**并行研究时，子代理拿到的是明确交给它的任务，以及父代理传下来的运行环境。** 代码为子代理新建消息列表，放入其系统说明、技能内容和一条任务消息 `HumanMessage(content=task)`，没有复制主代理此前的消息列表。因此，主代理需要在任务里说明研究目标、必要背景、约束和资料位置；不能只说“按我们刚才讨论的要求做”，就假定子代理知道前文。（T3-S04）

与此同时，父代理会传入 `sandbox`、`thread_data` 和 `thread_id`。这使子代理能够在相应工具允许的范围内使用同一线程的文件环境。**聊天上下文分开，文件环境却可以共用。** 例如，两个子代理可分别研究不同资料，把详细笔记写入不同的工作文件，再返回结论和文件位置。完成后，任务工具将子代理的结果返回主代理，由主代理综合为报告；这不是把子代理的完整对话历史合并回来。（T3-S04—T3-S06）

**上下文压缩发生在长对话内部。** 启用后，系统按配置的 token 数、消息数或输入窗口占比等条件触发压缩，把较早的消息整理成摘要，并保留近期消息及特定需要保留的内容。代码实际把当前消息列表替换成“摘要消息 + 保留消息”。它让后续模型调用有足够空间继续工作，但摘要不能保证保存每个细节；这段逻辑也没有把上传文件或报告变成长久记忆。（T3-S03、T3-S07、T3-S14）

压缩和长期记忆之间有一处配合：如果记忆功能开启，压缩前的钩子会筛选即将被压缩的消息，满足条件时送入记忆更新队列。这样，旧消息被摘要替换前，其中有价值的信息还有机会被提取出来。进入队列并不保证每句话都会被保存。（T3-S08、T3-S14）

**长期记忆保存的是提取后的背景、偏好和事实。** 正常回复完成后，记忆中间件筛选用户输入和最终回复，再交给后台队列处理；默认有 30 秒的合并等待时间，然后由模型提取、更新和去重。记忆文件包含工作背景、历史摘要，以及带类别和置信度的事实。它不是完整聊天记录，也不是上传资料的全文备份。（T3-S02、T3-S09）

记忆通常按用户保存；特定代理还可有自己的用户记忆。因此，几天后在同一用户、相应代理的范围内新建对话，若记忆已成功更新且注入开启，模型可能得到上次研究留下的背景或偏好。能带入多少内容受筛选和注入限制影响，不能理解为自动恢复上次所有研究细节。无认证模式下用户 ID 默认为 `default`；配置绝对 `storage_path` 也会退出默认的按用户隔离布局。（T3-S02）

这里代码比概述更具体：概述说“下次交互注入系统提示词”，实际动态上下文代码在新会话首轮用独立的 `HumanMessage` 放入含记忆和日期的提醒。同一天后续轮次不重新注入，跨天只补日期提醒，所以不能认为后台记忆一更新，当前对话的下一轮就一定重新读取。（T3-S10、T3-S11）

**新建对话后，旧资料不会自动出现。** 新的 `thread_id` 对应新的上传、工作和输出目录。旧文件即使仍在磁盘上，也不代表已进入新线程的文件视图；长期记忆中保留了某个结论，也不代表它能重新打开该结论所依据的旧附件。给定材料没有展示自动迁移旧附件或跨线程检索文件的机制，也没有说明旧文件的保留期限。因此，继续核对原始资料需要明确把资料带入新对话，不能仅依赖长期记忆。（T3-S03、T3-S12、T3-S13）

最后，本地模式的“线程隔离”主要体现为路径映射：例如线程 `abc` 获得 `local:abc`，把 `/mnt/user-data/...` 映射到该线程的宿主机目录，同一线程的调用复用相应 `LocalSandbox`。子代理继承父线程的信息，并不会因此各自创建一个独立容器。`AioSandboxProvider` 才提供容器内执行；本地模式不是安全隔离边界，所以默认关闭宿主机 `bash`。应分别理解“各自的聊天上下文”“按线程组织的文件目录”和“容器隔离”这三件事。（T3-S01、T3-S05、T3-S13）

### Y

子代理不会自动得到主代理此前的全部对话；新建对话也不会自动挂上旧对话的上传文件。本地模式的“线程隔离”是按对话分配目录和路径映射，并不等于每个子代理都有独立容器。

这里的 thread 可以理解为一段对话，由 `thread_id` 标识。沿着你“上传资料 → 并行研究 → 汇总报告 → 几天后再讨论”的流程看，几种机制各有分工：

| 机制 | 保存或传递什么 | 作用范围 |
| --- | --- | --- |
| 子代理上下文 | 系统说明、加载的技能、主代理交给它的任务，以及执行中形成的消息 | 各子代理自己的上下文 |
| `uploads/` | 上传资料；支持的文档会自动转换 | 当前对话的文件目录 |
| `workspace/` | 研究笔记、脚本、中间结果等工作文件 | 当前对话的文件目录 |
| `outputs/` | 报告等最终交付文件 | 当前对话的文件目录 |
| 上下文压缩 | 较早消息的摘要，以及保留下来的近期消息等 | 当前会话的消息状态 |
| 长期记忆 | 提取出的用户背景、偏好、历史概述和离散事实 | 默认按用户保存，可另按 agent 区分，供后续会话使用 |

上传后，资料进入该对话的 `uploads/`，`UploadsMiddleware` 把上传文件清单提供给代理。文件清单让代理知道资料在哪里，不等于把所有文件全文一直放在模型上下文里。（T3-S03、T3-S12）

主代理拆分研究任务时，需要在任务描述中明确交代问题、必要背景、资料路径和返回要求。执行器创建子代理的初始消息时，只加入系统说明、技能和这次任务，没有复制主代理的消息历史。不过，它会接收父代理的 `sandbox`、`thread_data` 和 `thread_id`，因此各子代理可以通过可用文件工具访问同一对话的资料和工作文件。**对话上下文独立，文件环境可以共享**；一个子代理写出的笔记，另一个仍需知道路径并主动读取，内容才会进入它自己的上下文。（T3-S04、T3-S05）

子代理完成后，任务工具把 `result.result` 返回主代理，主代理据此汇总。这里传回的是任务结果，不是自动合并子代理全部执行消息。实际安排可以是：各子代理在 `workspace/` 写不同的研究笔记，返回结论、来源及笔记路径；主代理读取需要的内容，再把最终报告写到 `outputs/`。由于文件共享，并行任务应避免同时覆盖同一个文件。（T3-S06）

研究持续很久时，若启用了上下文压缩，系统会按配置的 token 数、消息数或输入窗口比例触发摘要。代码把当前消息状态替换为“摘要消息 + 保留消息”，并有技能和动态提醒的保留处理。它缩短的是模型接下来看到的消息历史，不会把上传文件变成长久记忆，也不是在这里删除文件。摘要可能省略细节，所以已经落到工作文件中的证据仍有价值，需要时可以重新读取。（T3-S03、T3-S07、T3-S14）

长期记忆则负责跨会话的有限延续。启用后，代理结束时会筛选用户输入和最终回复，排队让模型提取值得保留的背景与事实；压缩发生前也会把即将被摘要的消息筛选后送入记忆队列。它不是逐字对话备份，也不会自动归档所有工具输出或上传文件全文。更新在后台进行，默认有约 30 秒的防抖等待；后续注入也受事实数量和 token 预算限制。（T3-S02、T3-S08、T3-S09）

关于注入时机，概述里写的是“下次交互注入系统提示”，但给出的具体代码更明确：首次注入把记忆和日期放进独立的 `HumanMessage` 提醒；同一天不重复注入，跨日只补日期。因此不能理解成每轮都重新加载最新记忆。记忆更新和记忆注入也分别受配置开关控制。（T3-S10、T3-S11）

几天后新建对话，会有新的 `thread_id` 和对应的文件目录。旧文件即使仍在磁盘上，也不代表新对话会自动列出、挂载或读取它们。长期记忆可能让代理记得你的报告主题、偏好或部分结论，但记住这些事实不等于能够访问原始资料。若要在新对话核对原文，需要重新上传，或通过明确的文件转移、访问安排把资料提供给新对话；给出的材料没有展示自动跨对话复用上传文件的机制。继续原对话与新建对话，在这一点上有区别。（T3-S02、T3-S12、T3-S13）

最后，本地 `LocalSandboxProvider` 为同一 `thread_id` 复用 `local:<thread_id>` 实例，把 `/mnt/user-data/...` 映射到该对话在宿主机上的目录。子代理继承父代理的环境，所以不能把它理解为“一子代理一容器”。容器内执行对应的是 `AioSandboxProvider`；材料也没有据此保证每个子代理各有容器。本地路径隔离不构成安全的执行隔离边界，这也是本地宿主机 `bash` 默认关闭的原因。（T3-S01、T3-S05、T3-S13）

## P04 · DeerFlow 长任务中的信息与状态

我会 Python，但第一次看 DeerFlow。假设我上传几份资料，让它并行研究、汇总出一份报告，过几天又新建对话继续讨论。我想弄清：子代理、workspace/uploads/outputs、上下文压缩和长期记忆分别保存或传递什么，它们之间怎么配合？子代理是否自动知道主代理之前的全部对话？新建对话后是否就能继续读取之前上传的资料？另外，本地模式里的线程隔离，是否等于每个子代理都在独立容器里？

### X

这里的“线程”可以理解为一段对话及其关联状态。你的研究任务会在这个线程里分工、读写文件、汇总结果；几天后新建对话，则会得到另一个线程。**子代理不会自动继承主代理的全部对话，新对话也不会自动获得旧线程的上传文件；本地线程隔离更不等于每个子代理各有一个容器。**

按你的任务过程看，这几套机制这样配合：

1. **上传资料后，文件归当前线程管理。** 上传接口带有 `thread_id`，文件保存在该线程的目录中，`UploadsMiddleware` 把上传文件列表告知代理。PDF、Word、PPT、Excel 等文档支持自动转换，但“获得文件列表”不等于全文已经进入模型上下文，代理仍需读取需要的内容。（T3-S03、S12）

   三个目录各有用途：

   | 目录 | 在研究任务中的用途 |
   | --- | --- |
   | `/mnt/user-data/uploads/` | 上传的参考资料 |
   | `/mnt/user-data/workspace/` | 工作文件，例如研究笔记、中间整理结果 |
   | `/mnt/user-data/outputs/` | 最终交付物，例如报告 |

   文件把大段资料和中间成果留在模型上下文之外；代理可以通过工具读取它们。上下文保存的是当前供模型使用的消息，文件保存的是磁盘上的内容，两者需要通过读写操作联系起来。（T3-S01）

2. **主代理拆分任务，子代理各自研究，再把结果交回。** 子代理启动时，消息列表由自己的系统提示、加载的技能和主代理传入的 `task` 构成，代码没有复制主代理的历史消息。因此，主代理必须在任务中交代研究目标、相关约束和所需资料位置；之前只在主对话中说过的要求，子代理不会自动知道。（T3-S04）

   但子代理会继承父代理的 `sandbox`、`thread_data` 和 `thread_id`，所以它们可以在工具权限允许的范围内使用同一线程的文件环境。**消息上下文各自独立，文件环境可以共享。** 例如，两个子代理可以分别读取两份上传资料，将笔记写到不同工作文件，再返回结论和文件位置。完成时，任务工具把子代理的结果返回给主代理，由主代理汇总；这并不是把子代理完整的内部对话接到主对话后面。（T3-S04—S06）

3. **研究过程很长时，上下文压缩负责让当前对话继续工作。** 启用后，它按配置的 token 数、消息数或输入容量比例触发，将较早消息总结成摘要，保留近期消息及部分需要保护的上下文。实现会用“摘要消息 + 保留的消息”替换当前消息列表。（T3-S03、S07、S14）

   这意味着模型之后主要依赖摘要理解较早的工作，不能假定每个原始细节都仍在眼前。压缩操作也不会把整个文件系统装入摘要，或把文件搬到新线程；详细资料和已写入文件的中间成果仍需通过文件工具读取。

4. **长期记忆把适合跨对话使用的信息另行保存。** 开启记忆后，代理完成一轮运行时，会筛选用户输入和最终回复，放入后台更新队列，再由模型提取用户背景、偏好、目标、知识等摘要和事实，写入本地 `memory.json`。默认队列有 30 秒的防抖等待，因此更新不是即时完成的，也不是逐字保存全部历史或上传文件。（T3-S02、S09）

   压缩与记忆还有一个连接点：启用记忆时，压缩前的钩子会把即将被总结的消息筛选后送入记忆队列。这样，较早内容有机会被提取成长期记忆，但并不保证其中每个细节都会保存。（T3-S08、S14）

几天后新建对话，长期记忆和文件的区别就很关键了。默认记忆按用户存储，也支持按用户、按代理分别存储；在相应范围内启用记忆注入时，新对话可以拿到已有的背景和事实，但注入有数量及 token 限制，不是恢复整个旧对话。材料概述说记忆进入系统提示，但具体代码是在首轮插入一条包含记忆和日期的独立 `HumanMessage` 提醒；同一天后续轮次不重复注入，跨日仅更新日期，因此也不能理解成每一轮都会重新加载最新记忆。（T3-S02、S10、S11）

旧资料则属于旧线程。新线程会计算自己的 `uploads/workspace/outputs` 路径，材料没有展示自动挂载或复制旧线程文件的机制。旧文件是否仍保存在磁盘上，与新对话是否能直接读取，是两个问题；长期记忆即使记住了研究主题，也不会因此带来原始附件。要在新对话中依据原文继续讨论，需要重新提供文件，或由系统通过明确的文件转移、访问机制提供它们；这些摘录没有说明这样的跨线程机制或文件保留期限。（T3-S12、S13）

最后，本地模式的隔离发生在**线程目录和路径映射**这一层：`LocalSandboxProvider` 为线程生成类似 `local:abc` 的沙箱标识，将 `/mnt/user-data/...` 映射到该线程的宿主机目录；同一线程会复用对应的 `LocalSandbox`。子代理又继承了父线程的沙箱状态，因此不能据此推导出“每个子代理一个独立容器”。本地模式不是安全的执行隔离边界，宿主机 `bash` 默认关闭；使用隔离容器执行 shell 的是 `AioSandboxProvider`，材料同样没有承诺按子代理分配容器。（T3-S01、S04、S13）

### Y

子代理不会自动继承主代理的全部对话；新建对话也不会自动接上旧对话的上传目录。本地模式的“线程隔离”指按对话分配目录和路径映射，不代表每个子代理有独立容器。

可以把这几部分分开理解：

| 部分 | 保存或传递什么 | 作用范围 |
|---|---|---|
| 子代理上下文 | 自己的系统说明、技能和主代理交给它的任务；完成后返回结果 | 一次委派任务 |
| `uploads` / `workspace` / `outputs` | 上传原件、工作文件和中间结果、最终交付物 | 当前对话的文件目录 |
| 上下文压缩 | 较早消息的摘要，加上保留的近期消息等 | 当前会话的模型输入 |
| 长期记忆 | 提炼后的用户背景、偏好、历史概述和事实 | 可跨会话，通常按用户、也可按 agent 保存 |

按你“上传资料→并行研究→汇总报告→几天后新建对话”的过程看：

1. **上传资料。** 上传接口带有 `thread_id`，文件进入这个对话的 `uploads`；支持的文档还会做转换，`UploadsMiddleware` 将上传文件清单交给代理。清单让它知道文件在哪里，不等于文件全文已经进入模型上下文。代理仍需要读取相关内容。（T3-S03、S12）

2. **主代理分派研究。** 子代理执行器从新的消息列表开始，加入系统说明、技能和一个包含委派任务的 `HumanMessage`，没有复制主代理的历史消息。因此，主代理需要在任务中交代研究问题、必要背景、约束和资料路径。代码同时传入父代理的 `sandbox`、`thread_data` 和 `thread_id`：子代理的对话上下文独立，但它们可以通过工具访问同一对话的文件。其他子代理写出的文件也不等于自动成为它的已知内容，仍需找到并读取。（T3-S04、S05）

3. **研究结果汇合。** 子代理完成后，`task` 工具把结果返回给主代理，由主代理汇总。较长的笔记和中间结果可以写在 `workspace`，最后的报告放在 `outputs`，并在返回结果中说明结论和文件位置。由于这里共用对话的文件环境，并行任务适合使用不同文件名或子目录，避免相互覆盖。（T3-S01、S06）

4. **任务变长时压缩上下文。** 启用总结功能后，达到配置的 token、消息数等阈值，就把较早消息改成摘要并保留近期消息；代码还处理技能内容和动态提醒的保留。它改变的是后续传给模型的消息状态，不是把文件内容搬进长期记忆，也不意味着删除上传文件。摘要可能遗漏细节，所以精确引用、数据和长篇笔记仍应以文件为依据。（T3-S03、S07、S14）

5. **提取长期记忆。** 启用记忆后，代理结束时会筛选用户输入和最终回答，放入后台队列，再由模型提取值得保存的背景与事实；压缩旧消息前也有一个入队钩子，给这些内容提供提取机会。它不是完整对话备份，也不会自动保存所有工具输出或上传文件全文。更新有默认约 30 秒的等待时间，保存与注入又有各自的开关，因此不能把“说过”直接当作“已经记住”。（T3-S02、S08、S09）

几天后新建对话，可能带过去的是**已经提取、保存并被选中注入的记忆**，不是旧对话的全部消息和文件。具体注入位置以代码为准：首次交互会加入一条包含记忆和日期的独立 `HumanMessage` 提醒；不是概述中所说的直接放进 system prompt，也不是每轮刷新记忆。同一会话跨日时，展示的代码只补日期提醒。（T3-S10、S11）

新对话有新的 `thread_id`，会解析到自己的 `uploads`、`workspace` 和 `outputs`。即使旧文件仍在磁盘上，也不能据此认为新对话自动能读取它们；给定材料没有展示跨对话自动挂载或导入旧资料的机制。要让新对话核对原文，需要重新上传或明确把所需文件带入新对话。记忆里保留某份资料的结论，不能替代对原文件的访问。（T3-S03、S12、S13）

最后，这里的“线程”是对话标识，不是每个子代理一个操作系统线程或容器。`LocalSandboxProvider` 为同一 `thread_id` 复用本地沙箱实例，将 `/mnt/user-data/...` 映射到该对话的宿主机目录；本地 `bash` 默认禁用，因为这种目录划分不是安全隔离边界。`AioSandboxProvider` 才在隔离容器内执行 shell，但子代理继承父代理沙箱状态的代码仍不支持“每个子代理自动获得独立容器”的理解。（T3-S01、S05、S13）

## P05 · Open SWE 请求到 PR

我会写 Python，但没有用过 LangGraph。我想理解 Open SWE：在 Slack 里让它修一个仓库的 bug 之后，消息、agent、线程和沙箱之间到底怎样配合，最后又怎么得到 PR？如果我在它工作时补充一句要求，和它完成后再回复一句，有什么区别？仓库里的 AGENTS.md 在哪里起作用？它说有自动开 PR 的兜底，这是否也意味着测试一定通过？

### X

Open SWE 把 Slack 请求接到一个能读写仓库、执行命令和提交 PR 的 agent 上。你可以先把 LangGraph 理解为管理对话状态和运行过程的服务：**thread 是持续的任务上下文，run 是其中一次运行，sandbox 是实际存放代码、执行命令的环境。** 同一个 thread 可以有多次 run，并复用沙箱；这里的 thread 不是 Python 的操作系统线程。

一次修 bug 的过程大致是：

```text
Slack 中 @机器人，指定 repo:owner/name 和问题
    ↓
入口整理请求与对话内容，定位 LangGraph thread
    ↓
在该 thread 上启动一次 run
    ↓
准备沙箱和仓库 → 读取根目录 AGENTS.md → 构建 agent
    ↓
agent 读取代码、修改文件、执行检查
    ↓
commit_and_open_pr 提交并推送，创建 GitHub 草稿 PR
    ↓
slack_thread_reply 把结果和 PR 链接发回原 Slack 讨论串
```

入口会用 Slack 的频道 ID 和讨论串时间戳生成稳定的 thread ID，所以同一讨论串的后续请求能找到同一份任务上下文。它把仓库、发起者、Slack 位置、对话内容和最新请求一起传入。README 概括为读取完整历史，但代码实际上先选择上下文，起点可能是讨论串开头，也可能是上一次提及机器人的消息，不能理解成每次都原样带上全部 Slack 历史。（T1-S02、S03）

沙箱按 thread 查找：先用缓存，或根据已记录的 sandbox ID 重连；没有时新建并克隆仓库，复用时会调用克隆或拉取逻辑。失联时可以重建。因而“完成后继续聊”通常能接着使用原来的工作环境，但“可重建”不等于原沙箱里未推送的文件一定能恢复。（T1-S06）

agent 本身由 `create_deep_agent` 构建，组合模型、工具、沙箱后端和 middleware。你可以把 middleware 理解为运行过程中特定时机执行的 Python 钩子，例如每次调用模型之前检查新消息、agent 结束后检查是否需要提交。模型决定如何排查和修改，工具负责实际读写与执行。Deep Agents 还提供 `task` 工具，让主 agent 分派独立子任务；材料没有说明每个子代理都会另建一个沙箱。（T1-S01、S07）

你补充要求时，要区分“已有 run 仍在运行”和“启动下一次 run”，还要看消息走哪条入口：

| 情况 | 这份代码能确认的行为 |
|---|---|
| 工作中有消息进入该 thread 的待处理队列 | `check_message_queue_before_model` 在下一次模型调用前读取队列，按顺序把内容合并成一条用户消息加入状态，并清空队列。它不会因为你发了一句话就立刻终止正在执行的 shell 命令。 |
| 工作中再次通过所示 Slack 提及入口触发 | 入口调用 `runs.create`，配置是 `multitask_strategy="interrupt"`，因此不能把这种情况一概说成“仅排队，当前 run 照常继续”。 |
| 完成后在同一 Slack 讨论串再次提及机器人 | 使用相同 thread ID 启动新的 run，通常复用该 thread 的沙箱；这是同一任务上下文中的新一轮工作。 |

README 宣称支持工作中接收补充，队列读取代码也确实存在；但所给材料没有展示 Slack 消息写入队列的分支，不能据此断言所有工作中的 Slack 补充都走队列。所示入口会过滤不符合提及条件的消息，所以普通回复一句、不 @机器人，也不能保证触发处理。（T1-S03～S05）

`AGENTS.md` 在沙箱准备好之后、构建 agent 之前起作用。程序读取的是沙箱中仓库根目录的 `AGENTS.md`，把非空内容放进 agent 的系统指令，用来传达编码规范、检查要求和架构约束。文件不存在或为空时就不加入；这里没有展示递归加载子目录 `AGENTS.md` 的机制。它影响模型如何做事，本身不是自动执行测试的程序。（T1-S07、S08、S12）

最后，**自动开 PR 的兜底不意味着测试一定通过，甚至不意味着任何情况下都一定能开出 PR。**

正常流程要求 agent 完成实现与检查，再调用 `commit_and_open_pr`；成功且返回链接后，通过 `slack_thread_reply` 通知你。README 将该工具描述为提交代码并创建草稿 PR。具体指令明确要求运行格式化、lint 和审查 diff，README 还提到测试；这些要求不能替代实际执行结果。（T1-S01、S10、S11）

而 `open_pr_if_needed` 的实际条件比 README 的概述窄：它先从历史消息里找 `commit_and_open_pr` 的工具结果，找不到有效载荷就直接退出；载荷只要含有 `success` 键，也直接退出，并没有判断其值是否为真。只有继续满足沙箱、仓库、未提交改动或未推送提交等条件，才会尝试提交；推送和创建 PR 还需要 GitHub token。其目标分支是 `open-swe/{thread_id}`，异常会被捕获并记录。（T1-S09）

这段兜底代码没有运行测试，也没有检查测试通过状态。因此，PR 链接证明的是提交产物已经形成；是否通过测试，要看实际检查结果和 CI 状态。

### Y

Open SWE 把 Slack 入口、可持续的对话状态、模型调用和远程代码环境接在一起。你可以先把 LangGraph 理解为负责组织执行、保存对话状态的运行层；Open SWE 在 Deep Agents 框架上配置模型、工具和执行前后的钩子。

这里有几个容易混淆的概念：

| 概念 | 在这次修 bug 中的作用 |
|---|---|
| Slack 消息与讨论串 | 用户发要求、补充说明、收取进度和 PR 链接的地方 |
| LangGraph thread | 后端的对话标识与状态归属；这里的 thread 不是 Python 的操作系统线程 |
| run | 在某个 thread 上发起的一次执行；同一 thread 可以先后运行多次 |
| agent | 模型加工具及控制逻辑，反复决定下一步、调用工具、读取结果 |
| sandbox | 实际存放仓库、修改文件和执行 shell 命令的远程 Linux 环境 |

一次请求大致这样走：

1. **Slack 入口整理请求。** 你提及机器人，可用 `repo:owner/name` 指定仓库。入口用频道 ID 和讨论串时间戳生成确定的后端 thread ID，因此同一 Slack 讨论串会映射回同一个后端 thread。它获取讨论串消息，把仓库、发起人、上下文和最新要求组装成用户消息，再调用 `runs.create(thread_id, "agent", ...)`。实际代码会选择上下文，可能从上次提及机器人处开始，不能把 README 的“完整历史”理解为每次都传入全部消息。[T1-S01–S04]
2. **为这个 thread 准备沙箱。** 服务先找缓存中的后端或元数据里的 sandbox ID：能用就复用或重新连接；没有就创建，并把仓库克隆进去。复用时会尝试拉取仓库更新；沙箱无法连接时可以重建。因此后续回复通常延续同一工作环境，但这不等于沙箱里的未提交文件永远不会丢失。[T1-S06]
3. **创建 agent 并执行工作。** 服务把沙箱作为 Deep Agents 的 backend，配上文件操作、shell、PR 提交及 Slack 回复等工具。模型据此读代码、修改文件、执行检查，再根据工具结果继续。执行钩子则在模型调用前或 agent 结束后运行固定逻辑。框架还支持用 `task` 委派子任务，但不是每次修 bug 都必须使用子代理，也不能据此认定每个子代理都有独立沙箱。[T1-S01、S07]
4. **提交并把结果发回 Slack。** 正常流程要求 agent 完成检查后调用 `commit_and_open_pr`，由它提交、推送并创建 GitHub 草稿 PR；成功后调用 `slack_thread_reply` 发回摘要和链接。提示明确要求：只有工具返回成功和 PR 链接，才能宣称 PR 已创建或更新；无改动或出错则应如实报告。[T1-S01、S10–S11]

**工作中补充要求，与完成后回复，区别在于是否还存在可继续推进的当前执行。**

工作中，项目提供了消息队列机制：`check_message_queue_before_model` 在下一次模型调用前读取该 thread 的待处理消息，按先后顺序合并为一条新的用户消息，加入对话状态并清空队列。对于走这条路径的补充，模型会在下一步看到它；这不表示正在执行的 shell 命令会立即停止或撤销。[T1-S05]

但给出的代码还揭示了另一点：Slack 的 `runs.create` 设置了 `multitask_strategy="interrupt"`。因此，不能仅凭 README 就断言“工作中所有 Slack 补充都只入队、绝不中断当前 run”。材料展示了队列消费和可中断的运行创建，却没有完整展示 Slack 消息何时入队、何时创建 run 的分流代码；具体消息走哪条路径，不能从这些摘录确定。[T1-S03、S05]

完成后再在同一讨论串提及机器人，会以同一 thread ID 发起后续 run，通常复用该 thread 的沙箱。它是同一对话下的新一次执行，不是让已经结束的 run 继续停在那里等消息。另外，给出的入口会忽略没有提及机器人的事件，所以普通回复一句话不能保证触发工作。[T1-S02–S04、S06]

**`AGENTS.md` 在准备 agent 时进入模型上下文。** 仓库准备好后，服务读取沙箱中仓库根目录的 `AGENTS.md`，把内容放进系统提示的 `<agents_md>` 段，再创建 agent。你可以在那里写项目约定、测试要求和架构限制；文件不存在或为空就不注入。这段实现只明确读取根目录文件，没有展示递归查找各子目录规则。它向模型提供行为要求，本身不是自动执行测试的程序。[T1-S07–S08、S12]

**自动开 PR 的兜底不意味着测试一定通过，甚至也不是无条件保证产出 PR。** README 的描述比给出的实现更宽泛。实际 `open_pr_if_needed` 会先查找 `commit_and_open_pr` 的工具返回内容：

- 找不到可用的返回内容，就跳过。
- 返回内容只要含有 `success` 键，就跳过；代码并没有检查它的值是否为真。
- 剩下的情况还要满足 thread、沙箱、仓库和改动等条件；推送与创建 PR 需要 GitHub token，异常会被捕获并记录。

满足条件后，它才尝试切到 `open-swe/{thread_id}` 分支、提交、推送并创建 PR。该兜底代码没有运行测试，也没有检查测试或 CI 是否通过。[T1-S09]

README 说 agent 被要求运行测试，给出的提示片段明确要求格式化、lint 和检查 diff；这些属于对模型的要求。PR 是否存在、检查是否实际执行、测试是否通过，是需要分别确认的结果。这里展示的实现没有把“测试通过”设成开 PR 的强制程序门槛。[T1-S01、S09–S11]

## P06 · 三个项目的定位与选择

我看了 deepagents、Open SWE 和 DeerFlow，感觉它们都支持工具、子代理和沙箱，分不清到底是什么关系。我会 Python，也懂普通 Web 应用，但不熟悉 agent 框架。现在要做一个团队内部代码助手：同事从工作沟通工具发任务，它在隔离环境里改代码，产出供人审查的 PR。这三个项目分别能给我什么，需要自己补什么？它们是互相替代的选择，还是可以叠在一起？请结合这个目标给出判断，材料无法确定的地方也说明。

### X

就你的目标——“同事从工作沟通工具发任务 → 在隔离环境里改代码 → 提交供人审查的 PR”——**Open SWE 是最直接的起点**。deepagents 是它已经采用的通用 agent 底座；DeerFlow 则是另一套带 Web 界面和沟通工具接入的通用 agent 系统，也能作为起点，但给定材料没有展示完整的代码到 PR 流程。

三者有重叠，但不处于完全相同的层次。这里的 agent harness 可以理解为：替模型安排工具调用、任务拆分、上下文管理等工作的运行骨架。LangGraph 是这些系统使用的运行基础；你不必先理解它的全部概念，才能区分三个项目。

| 项目 | 已经提供什么 | 对你的代码助手还需补什么 |
|---|---|---|
| **deepagents** | Python 中调用 `create_deep_agent()` 即可创建 agent，带计划、文件操作、子代理和上下文管理；可定制模型、工具和后端，返回可使用 LangGraph 持久化等能力的运行图。 | 工作沟通工具入口、消息与任务的对应关系、仓库准备、隔离执行后端、GitHub 提交与 PR 流程，以及团队权限和验证规则。材料展示的是可供组合的能力，没有展示你的完整业务流程。 |
| **Open SWE** | 在 deepagents 上加入面向代码任务的流程：Slack/Linear 发起任务、收集来源上下文、按线程使用云沙箱、提交代码并创建 GitHub 草稿 PR、向原会话回报，还支持在其创建的 PR 中处理审查反馈。 | 部署和接入配置、仓库及沙箱环境、团队访问权限、凭据范围，以及强制执行的 CI 和审查门槛。若入口是飞书或钉钉，材料未展示现成支持，需要适配。 |
| **DeerFlow** | 通用 agent 能力之外，还有 Gateway API、Next.js Web 界面、技能、长期记忆、文件与沙箱管理，以及飞书、Slack、Telegram、钉钉接入。后端明确拆成可发布的 harness 和应用层。 | 面向代码的仓库准备、分支管理、提交与 PR 工具、PR 审查反馈处理，以及测试和权限策略。给定材料没有证明这些已经组成开箱可用的代码助手流程。 |

以上分别依据 T2-S01～S03、S04～S07、S08～S12。特别注意，deepagents README 中搜索、远程沙箱、持久记忆和人工审批的一段介绍指向它的 **CLI**，不能把这些全部当成一次默认 Python 调用就已完成的服务端配置。

用 Open SWE 时，你需要搭建的主流程已经比较接近成品：

1. 同事在 Slack 中提及机器人，并可通过 `repo:owner/name` 指定仓库；系统把 Slack 线程历史作为任务上下文。
2. 同一来源线程被映射到确定的 agent 线程 ID；每个线程有可供后续消息复用的沙箱，仓库在其中准备好。
3. agent 使用 deepagents 的文件、命令和子代理工具开展工作。仓库根目录的 `AGENTS.md` 会从沙箱读入并加入系统提示，可放入仓库约定和测试要求。
4. `commit_and_open_pr` 提交修改并创建 GitHub 草稿 PR，机器人将结果回传。工作中追加的消息由中间件在下一次模型调用前注入；PR 中的审查反馈也有继续修改同一分支的入口。（T2-S05～S07）

这里有两个会影响落地的边界。

**能创建 PR，不等于测试已经通过。** Open SWE 要求 agent 在提交前运行格式检查、lint 和测试，但材料将其描述为提示驱动。`open_pr_if_needed` 的兜底职责是补做提交和开 PR，没有证据表明它是“测试全绿才允许提交”的硬门槛。供人审查的草稿 PR 可以是中间产物；如果团队要求通过检查才能合并，就需要确定性的 CI 和审查规则。（T2-S05）

**有文件目录隔离，也不一定有执行隔离。** DeerFlow 的 `AioSandboxProvider` 在隔离容器中执行命令；`LocalSandboxProvider` 只是把文件工具映射到宿主机的线程目录，宿主机 bash 默认关闭，因为这不构成安全隔离。你的目标包含隔离环境，不能仅凭“每个线程有自己的目录”满足它。Open SWE 提供云沙箱模式，但其 README 对风险被完全控制的表述，也不能替代对实际凭据、网络和挂载配置的检查。（T2-S05、S09）

它们的组合关系也很明确：

- **Open SWE + deepagents 是现有关系**，不是需要你重新设计的集成。选择 Open SWE，就已经在使用 deepagents；可通过工具、提示和中间件定制组织流程。
- **DeerFlow 是另一条构建应用的路线**。它的 harness 负责 agent 能力，应用层负责 Gateway 和沟通工具接入。材料说明它基于 LangGraph/LangChain，没有证据表明它基于 deepagents 或 Open SWE。
- **把 DeerFlow 和 Open SWE 再叠起来并非现成能力**。可以设想让一个应用调用另一个服务，但消息路由、线程归属、沙箱生命周期和结果回传都需要明确设计。共享 LangGraph 基础并不等于可以直接拼接。

因此，如果团队使用 Slack，且主要交付物就是代码 PR，我会先选 **Open SWE，在其上补齐组织接入和强制验证**。如果飞书或钉钉是关键入口，或者你同时需要研究、报告、文件交付和 Web 界面，DeerFlow 更值得纳入候选；此时要比较“给 Open SWE 增加沟通工具入口”和“给 DeerFlow 增加代码到 PR 流程”的实际成本。只有当你希望自己控制整个应用架构，并愿意承担这些集成工作时，才更适合直接从 deepagents 搭建。

这些判断基于给定快照中的架构和流程证据。材料没有性能、成本或代码修复成功率对比，也不足以确定各项目在你们仓库、权限体系和并发规模下的运行表现。

### Y

针对“同事从沟通工具派任务 → 在隔离环境改代码 → 提交 PR 供人审查”，**Open SWE 是最贴近目标的起点**。deepagents 是它使用的通用代理基础；DeerFlow 则提供另一套通用代理系统和完整应用。三者能力有重叠，但所处层次和已经接好的工作流程不同。

你可以把这里的 harness 理解成“驱动模型持续工作的运行框架”：模型决定下一步，框架负责执行工具、维护上下文、调度子代理。这相当于普通 Web 开发中，应用下面的一层框架；具备框架能力，还不等于已经有了你的业务应用。

| 项目 | 已经能给你什么 | 为实现内部代码助手，还需要补什么 |
| --- | --- | --- |
| **deepagents** | Python 接口，可配置模型和工具；内置计划、文件操作、子代理和上下文管理。返回 LangGraph 的可执行图，可接入其流式输出、持久化和检查点能力。 | 沟通工具入口、任务与会话路由、仓库获取、隔离执行环境接入、Git 提交与 PR 流程，以及团队权限和检查规则。 |
| **Open SWE** | 已基于 deepagents 接好面向代码任务的流程：Slack/Linear 入口、线程上下文、云沙箱、仓库规则、GitHub 草稿 PR，以及从 PR 评论接收修改意见。 | 配置模型、沙箱和平台凭据，接入团队仓库与规范；补充可靠的质量门槛和权限配置。若用的是飞书、钉钉等未列出的入口，还需做适配。 |
| **DeerFlow** | 通用代理框架加完整应用：Web 界面、Gateway、技能、记忆、工具、子代理和沙箱支持；应用层已有飞书、Slack、Telegram、钉钉通道。 | 将代码任务做成稳定流程，包括仓库准备、分支与提交、PR 创建和审查反馈处理。给定材料没有证明这些已经像 Open SWE 那样接好。 |

依据：T2-S01～S07、T2-S08～S12。

**它们可以在哪一层叠加？**

已明确存在的关系是：**Open SWE → deepagents → LangGraph**。Open SWE 直接调用 `create_deep_agent(...)`，注入自己的工具、沙箱后端和中间件，因此选 Open SWE 已经是在用 deepagents，不需要再把两者当作独立产品拼一次。（T2-S05）

DeerFlow 则基于 LangGraph 和 LangChain，内部也分为两层：可发布的 `deerflow-harness` 框架，以及提供 Gateway 和沟通工具通道的应用层。材料没有显示它依赖 deepagents 或 Open SWE，也没有提供三者直接组合的接口。它的框架层与 deepagents 有重叠，应用层与 Open SWE 也有部分重叠，但面向的任务更广，包括研究、报告、幻灯片和网页等。（T2-S08、T2-S11）

所以，**这不是三个完全互斥的同层选项，也不是应当全部叠上的三层架构**。如果从 DeerFlow 借用沟通工具接入、从 Open SWE 借用代码流程，你仍需自己处理会话、运行状态、工具和沙箱之间的衔接；给定材料不足以认定这种组合比单独扩展一个项目更省事。

有三处边界会直接影响你的选择：

- **有沙箱工具，不代表默认就获得了安全隔离。** deepagents 的默认示例不能证明已经配置好你的隔离执行环境，README 中部分审批和远程沙箱能力还属于 CLI 的介绍。Open SWE 明确接入云沙箱，同一线程可复用沙箱；DeerFlow 则要区分提供者：`AioSandboxProvider` 在隔离容器中执行 shell，`LocalSandboxProvider` 只是将文件操作映射到宿主机的线程目录，宿主机 bash 默认关闭，不能把它视为安全隔离边界。（T2-S02、S03、S05、S09）
- **产出 PR 和通过验证是两回事。** Open SWE 的 `commit_and_open_pr` 创建 GitHub 草稿 PR，符合先交人审查的目标；`open_pr_if_needed` 提供提交 PR 的兜底。但测试、格式化和 lint 在材料中主要靠指令要求模型执行，兜底开 PR 并不等于检查通过。要让“检查未通过就不能合并”成为硬规则，仍应接入确定性的 CI 和审查门槛。（T2-S05～S07）
- **子代理的上下文隔离，不等于执行环境或团队权限隔离。** 各项目描述了子代理独立上下文，但这些材料不足以证明每个子代理都有独立沙箱，也不足以确认完整的团队用户授权、凭据隔离和审计机制。Open SWE 文档中“影响完全受限”的概述，也不能代替对实际沙箱权限和网络配置的核查。

我的判断是：**若团队使用 Slack、代码托管在 GitHub，优先基于 Open SWE 定制**，因为它已经覆盖了你要的主要业务链路；会 Python 可以用于修改工具和流程，无需先自行搭建整套代理运行机制。若飞书或钉钉入口是硬要求，DeerFlow 的现有通道有实际价值，但需要在“为 Open SWE 补入口”和“为 DeerFlow 补代码交付流程”之间权衡，材料不能确定哪条总成本更低。直接选 deepagents，适合你希望自己掌控整个应用设计、愿意承担这些集成工作的时候。

这些材料能支持上述架构和适配判断，不能支持三者在代码修改成功率、运行成本、并发稳定性或生产安全性上的排名。
